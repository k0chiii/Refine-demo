# Material 3 Expressive 適用（UI 再構築）

実施: 2026-10-13。対象は `apps/web` のみ。PDF 表示・注釈座標・認証・業務ロジック（domain / application / convex / api）には変更を加えていない。

## 1. 調査で指摘された P0: テーマの適用範囲

### 事実確認（Computed Style）

`@m3e/web@2.9.2` の `m3e-theme` は、**`<body>` の直下にあるときだけ** テーマ変数を `html` に、フォントと背景色を `body` に適用する。それ以外の位置では自身の shadow root に `:host { … }` として閉じる（`theme.js` の `replaceSync` 分岐）。v0/v1 では React の `#root` の内側に `<M3eTheme>` を置いていたため、`:root` で定義した `--mf-*` の `var(--md-sys-color-*, fallback)` は **常にフォールバック値**に落ちていた。

| 計測点                                        | 改修前                       | 改修後（ライト）                              | 改修後（ダーク） |
| --------------------------------------------- | ---------------------------- | --------------------------------------------- | ---------------- |
| `m3e-theme` の親要素                          | `DIV`（#root 内）            | `BODY`                                        | `BODY`           |
| `html` の `--md-sys-color-primary`            | （未定義）                   | `#2b5ea8`                                     | `#bcd2ff`        |
| `.shell` の `--mf-primary`（独自 CSS が参照） | `#005cbb`（フォールバック）  | `#2b5ea8`                                     | `#bcd2ff`        |
| `body` の背景                                 | `rgb(247,249,251)`（固定値） | `rgb(249,249,255)` = `--md-sys-color-surface` | `rgb(7,14,27)`   |
| `body` のフォント                             | Noto Sans JP                 | Noto Sans JP                                  | Noto Sans JP     |

計測はデモモードで Playwright から `getComputedStyle` を取得した（`apps/web/e2e/screenshots.mjs` と同じ経路）。

### 修正

- `apps/web/index.html`: `<m3e-theme color="#1b5fb4" variant="expressive" scheme="auto" motion="expressive" strong-focus>` を `<body>` 直下に置き、その中に `#root`。設定値は `src/theme.ts` に集約（`<M3eTheme>` は `__root.tsx` から削除）。
- `src/styles.css`: 独自変数 `--mf-*` はすべて `--md-sys-color-*` の別名にし、M3 の色役割（surface-container 階層、primary/secondary/tertiary container、error、inverse）を揃えた。`scheme="auto"` によりダークモードは自動（画面 #20）。
- M3 に無い「成功」「注意」は固定の補助色（ライト／ダーク別）にした。動的カラーの tertiary/secondary は seed 次第で緑になるため、「未完了」を tertiary で塗ると意味が崩れる（実際にそうなったので修正）。重大（critical）だけは M3 の error を使う。

## 2. フォーム共通部品の再設計（P0）

`src/ui/Field.tsx` を M3E ベースに置き換えた。入力そのものは native を維持する（日本語 IME・キーボード操作・ブラウザ標準の検証を優先）。

| 部品                      | 実装                                                                                                                                                              |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Field`                   | `m3e-form-field`（outlined, float-label=always）。label / hint / error を slot に置き、`useId` で生成した id を子の入力と `label[for]` / `aria-labelledby` に配線 |
| `TextInput` / `TextArea`  | native `input` / `textarea`（form-field の既定 slot）                                                                                                             |
| `Select`                  | `m3e-select` + `m3e-option`。`<option>` 子要素をそのまま受け取り写すので呼び出し側は無変更                                                                        |
| `Checkbox`                | `m3e-checkbox` + label（`aria-labelledby`）                                                                                                                       |
| 検索                      | `m3e-search-bar`（制作物一覧・管理のユーザー検索）                                                                                                                |
| ユーザー選択 `UserPicker` | 選択済みは `m3e-input-chip`（removable）、検索欄は form-field、候補は listbox                                                                                     |

この差し替えだけで、登録・編集・提出・サインイン・ACL・指摘投稿の全フォームが Material の外観になった。

### 塗りとチップの削減（作法）

- **色付きチップは「操作を左右する状態」1 つだけ**（受付中／受付終了、未確認／確認完了、進行中／校了、転送状態）。それ以外（版、種別、件数、担当、ファイル名、持越）は文字（`.meta`）。

## 9. 3 回目の見直し（2026-10-13・「Google と同じアカウント表示」「テーマ切替をやめる」「飾りを無くす」）

- **アカウント**: 右上を Google と同じアバター表示にし、アバターは利用者指定の **Humation**（`@humation/react` + `@humation/assets-humation-1`。メール or ID を seed に決定的に同じ絵を描く、約 700KB のアセットは初回表示時に遅延読み込み）。クリックで氏名・メール・サインアウトのメニュー（`m3e-menu`）。`m3e-app-bar` の slot 外に置いた子は描画されないため、メニュー本体はアプリバーの外に置き、`m3e-menu-trigger` の `for` で結ぶ。
- **テーマ固定**: `scheme="light"`。自動切替・ダークモードの撮影・ダーク用の補助色を廃止。
- **飾りの削除**: ボタンの先頭アイコン（主要操作の「＋」「送信」「位置指定」を除く）、案内文・空状態・カード見出しのアイコン、状態チップのアイコン、版提出のステッパー、タイトル横の件数バッジ、サインインのロゴ、指摘カードのホバー影、サインインの背景グラデーションを削除。残るアイコンはナビゲーション、検索、カレンダー、アカウント、ピン位置、ツールバーなど意味のあるものだけ。
- M3E が読まない書体トークン（`--md-sys-typescale-font` 等）を削除。
- **アイコンのアニメーション**: Material Symbols の可変軸（FILL / wght）を CSS transition（350ms, standard easing）で連続的に変化させる。ナビの選択時は輪郭 → 塗り（FILL 0→1, wght 400→500）、ホバーで太さが増す。`prefers-reduced-motion` では無効。Playwright で遷移中の中間値（FILL 0.2 など）を確認済み。
- **アバターは Humation**: `src/ui/UserAvatar.tsx`。メニュー内の 2 つ目は装飾（`aria-hidden`）にして `role=img` が menu の子にならないようにした。

- **compact の余白は 16 で確定**（Breakpoints › Compact「Margins are 16dp from the leading and trailing edge of the window」）。medium 以上は 24。
- **Scaffold の原文**: 「bars はページを縁取る（アプリバー・下部ナビ）。bars は 1 ペインの幅でも窓の全幅でもよい」「rails は bars の次の層で、ペインの外周を埋める。compact では上下の rail 領域にツールバー・チャット入力・FAB、大きい画面では先頭側の rail にナビゲーションレール、末尾側に内容を操作する縦ツールバー」「panes は 1–3。推奨数: compact 1 / medium 1（2 可）/ expanded 2 / large 2 / extra-large 2（1, 3 可）」。
- **pane の型**: fixed（幅が変わらない）/ flexible（空きで伸縮。少なくとも 1 つ必要）、permanent / temporary、表示は co-planar（並置）/ floating（上に浮く。一時的な作業はどの幅でも floating）/ docked（窓端に固定。ボトムシートなど）。適応は show and hide / levitate / reflow。推奨の固定幅は 360 と 412（extra-large の固定ペインは 412、サイドシートは最大 400）。
- 本システムの当てはめ: エディタの引き出しは **fixed + temporary + co-planar**（expanded 360 / large 412）、compact では **docked**（ボトムシート）。通知パネルは **floating + temporary**（幅 360）、compact では **docked**（§14）。
- 未実装のまま: リサイズ可能なペインのドラッグハンドル（M3 は「ハンドルで折りたたみ・展開」を推奨）。

## 16. 検索バーを一旦外す・レールのヘッダーをアプリバーに揃える（2026-10-14・利用者指摘）

- **検索バー**: 利用者判断で一旦外した。部品は `features/work/WorkSearch.tsx` に残し、制作物一覧の `?q=` も残してある（戻すときは `_app.tsx` の題名スロットに置く）。アプリバーは題名も検索も無く、medium 以上はベル＋アカウント、compact はアカウントだけ。
- **高さが揃っていなかった理由**: M3 Navigation rail の規定「上端からヘッダー（メニュー）まで 44dp」を M3E がそのまま既定（`--m3e-nav-rail-top-space`）にしており、44 ＋ ボタン 40 の中心 ＝ 64 で、アプリバー（64）のアイコン中心 32 と 32 ずれていた。44 は Android のステータスバーを含む前提の値。
- **対応**: web ではステータスバーが無いので、レールの上余白を 12 にして メニューの中心を 32 に揃えた（12 ＋ 40 / 2）。FAB と行き先はそのぶん上に詰まる（ヘッダーと FAB の間隔 16 は M3E 既定のまま）。
- **アイコンの位置が動いて見えた理由**: 選択で太さ（wght）を 400 → 500、ホバーで 600 に変えていたため、字面が外側へ膨らんで動いて見えていた（枠の位置は実測で不変: アイコン x=36、幅 24）。M3 の active icon は「塗り（filled）」であって太さは変えない。wght を常に 400 にし、FILL だけを変化させるようにした。
- **折りたたみレールのラベル**: M3 Navigation rail は「すべての項目に 1 語のラベル」を求め、折りたたみ時はアイコンの下に置く（折り返しは避け、縮小も切り詰めもしない）。「ダッシュボード」は 1 語だが幅 88 でレール 96 のほぼ全幅。短くするなら「ホーム」などに差し替える。

### 実装

- 共通アプリバーは 1 本（`_app.tsx`）。`#appbar-leading / -title / -subtitle / -actions` の受け皿を置き、画面側が `ui/AppBarSlot.tsx`（portal）で差し込む。どの画面も見出しを差し込む（§18）。
- エディタの高さは `100dvh − 64`（以前はアプリバー 64 ＋見出し行 48 ＋余白）。compact のエディタ専用アプリバーは廃止して同じ仕組みに統一。
- 縦ツールバーは `.ws__side-toolbar`（`m3e-toolbar vertical`、紙面ペインの内側に絶対配置なので幅を取らない）。
- **「ラベルが動く」の再計測（同日）**: 折りたたみレールで、読み込み・項目の選択（遷移）・ホバー・展開⇄折りたたみの各場面で、アイコンとラベルの座標を 1 フレームごとに記録した。結果: 選択とホバーでは 1 フレームも動かない（選択のインジケーターとホバーの状態レイヤーはどちらも 56×32 で同じ高さ）。動くのは (1) **描画直後にアイコンが 4px 滑る**（M3E の slide-down / slide-up、約 200ms）、(2) **展開⇄折りたたみ**でアイコンが 6px、ラベルが下から横へ移る（項目の高さが 68 → 56 に変わる M3 の設計）。ラベルの折り返しは、代替フォントや字間を広げても 96 に収まり起きない。
- **対応**: レールと下部バーの中で M3E の短い motion（short-1 / short-2 / medium-1）を 0ms にし、アイコンの塗りの連続変化（350ms）もやめて即時にした。再計測で読み込み・遷移・ホバーは常に 1 状態。展開⇄折りたたみの移動だけが残る（これは M3 の仕様）。
- **利用者のスクリーンショットで再確認（同日）**: 折りたたみ状態の中ではラベルはアイコン下端から 22 / 23 px で同じ。動いていたのは**展開⇄折りたたみ**で、M3E の折りたたみ項目（68、アイコンの下にラベル）と展開項目（56、横にラベル）の高さ差のため、アイコンが上下に 5–10 px 移動していた。
- **対応（利用者判断で M3 Expressive から外れる）**: 折りたたみ時は**アイコンだけ**にし（ラベルは `title` と `aria-label`。下部バーのラベルは残す）、項目の高さを展開時と同じ 56、アイコンの中心を両状態で同じ y に固定した（`--m3e-vertical-nav-item-active-indicator-margin: 12`）。実測: 折りたたみ・展開ともアイコン中心 168 / 224、FAB 68。展開で変わるのはインジケーター（56×32 → 56 高）とラベルの出現だけ。M3 Expressive は「折りたたみでも 1 語のラベル」を求めるが、Google ドライブの実装と同じアイコンのみ方式を採った。
- **アニメーションの復活（同日、利用者希望）**: アイコンの輪郭 → 塗りと太さの連続変化、レール内の M3E モーション（描画時のスライド・ラベルのフェード）を元に戻した。位置ずれの原因は展開⇄折りたたみの項目の高さ差で、折りたたみレールをアイコンのみ・高さ 56 に揃えたことで解消済みのため、アニメーションを止める必要はなくなった。
- **設計原則（利用者決定・同日）: ナビのアイコンの高さは一切動かさない（Gmail と同じ）**。「高さが動かないなら、アイコンが上下に動く必要もない」を原則にした。
  - 静止位置: 折りたたみレールはアイコンのみ（ラベルは `title` / `aria-label` のツールチップ、`.nav-label` は非表示）にして、折りたたみ・展開のどちらでも項目の高さを 56 に揃え、アイコンの中心を同じ y に置く。ラベルの有無は任されたので、動かないことを優先してこの形にした。
  - 一瞬の動き: M3E が縦方向に入れる短い動き（選択時の 4px スライド ＝ `short-2`、向き変更時の margin の遷移 ＝ `short-1`）だけを、レールと下部バーの中で 0ms にした。`medium-1` 以降はそのまま。
  - 残した動き（利用者要望「元のアニメーションは消さないで」）: インジケーターの横方向の伸縮、ラベルのフェード、アイコンの塗り・太さの連続変化（350ms）、リップル。どれも高さを変えない。
  - 再計測（1 フレームごとにアイコンの y を記録）: 読み込みは `[] → [156, 212]` の 1 回だけ（描画前→後）。選択・ホバー・展開・展開中の選択・折りたたみはすべて 1 状態 `[156, 212]`。compact の下部バーの選択も 1 状態 `[857, 857, 857]`。

## 19. 版比較中のコメント・紙面の連続表示と自動フィット（2026-10-14・利用者指摘）

### M3 の規定（Canonical examples › Supporting pane。ax で本文 JSON を取得）

- 「supporting pane は内容を主（primary）と副（secondary）に分ける。主が大半を占め、副は主を支える内容」。**主な用途に「文書の編集とコメント（Document editing and commenting）」が挙がっている**。
- 「副の内容が主に対してだけ意味を持つときに使う」（親子関係なら list-detail）。
- 置き場所: compact / medium は主の下（幅は可変。compact はボトムシートが有効）、expanded は主の先頭側か末尾側（**固定 360dp**）。
- → 校正画面は supporting pane。主＝紙面（比較中は 2 版を並べた全体）、副＝コメント／版／情報の引き出し。比較は主の中の見せ方なので、主の操作（範囲・ピンでのコメント）を止める理由は無い。

### ズームでの視点の同期（2026-10-15・利用者指摘「ズームでの視点の位置も同期できるようにして欲しい」）

- 倍率は左右で共通（− ＋・倍率のメニュー・幅に合わせる・ピンチ・Ctrl＋ホイールのどれでも両方の版に掛かる）。実際の大きさは各版を幅に合わせた大きさ × 倍率なので、紙面の大きさが同じなら左右は同じ大きさになる（大きさが違う版は各版の幅合わせのまま）。
- 拡大縮小では焦点の下の箇所を同じ画面位置に保つ。焦点はピンチなら指の中点、Ctrl＋ホイールならポインタ、ボタン・メニューは舞台の中央。PDF・画像のビューアは描き直す前に「ページと、ページ内の縦・横の割合」を控え、描き直した直後にその箇所を焦点へ戻す（`features/annotation/viewerSync.ts`）。
- 同期が ON なら、操作した側（ピンチ・ホイールの側。ボタンは最後に操作していた側）の焦点の箇所を、もう一方の舞台の同じ割合の点に合わせる。PDF はページ対応・行のアンカーで写し（横はページ内の割合をそのまま）、画像は画像内の割合をそのまま写す（`domain/comparison/scrollSync.ts` の `mapPosition`・`mapImagePosition`・`relAt`・`alignShift`）。
- スクロールの同期も縦・横の両方（基準は舞台の横の中央・上から 40% の線）。プログラムからのスクロールは 120ms 利用者の操作として扱わないので往復しない。同期の切り替えは画像の比較（左右に並べるとき）にも出す。OFF でも倍率は共通で、位置だけ合わせない。重ねて比較（スワイプ）は従来どおり。
- 撮影スクリプトの 25（版の比較）で、2 回拡大して右をスクロールした後、左右の舞台の中央に紙面の同じ箇所（ページ内の縦・横の割合の差 0.02 未満）が来ることを検証している。

### 表（DataTable）と編集できるセル

M3 / M3E に data table が無いので、Material の data table（MDC `mdc-data-table/_data-table-theme.scss`）の寸法を M3 のトークンで組んだ `apps/web/src/ui/DataTable.tsx` に統一した: 見出し 56px（title-small）・行 52px・セルの左右 16px・区切り outline-variant 1px・外枠 shape medium・hover は on-surface 8% の state layer・選択行 secondary-container・見出しを押して並べ替え（`aria-sort`）・溢れたら表だけ横スクロール。表を囲むカードは使わず（枠が二重になる）、見出し（title-medium）＋表にした。

編集できるセルは 3 種類。どれも保存中・失敗をセルの中に出し、表を離れずに直せる。編集できない人には値だけを出す。

- `EditableText`: 押すと入力欄（Enter・フォーカスを外すと保存、Esc で取消、IME 変換中の Enter は無視）。入力の検査（`validate`）の結果はセルの中に `role="alert"` で出す
- `EditableSelect`: `m3e-select` をセルの中にそのまま置く
- `EditableSwitch`: `m3e-switch`（`icons="selected"`）

## 25. スマホでのコメント: 長押し→なぞって範囲選択、バウンススクロールを止める（2026-10-14・利用者指示）

- **PDF・画像（`AnchorOverlay`）**: 以前はコメント層が `touch-action: none` で、指でなぞると必ず範囲選択になりスクロールできなかった。タッチは次のように変えた（マウス・ペンは従来どおり、ドラッグで範囲・クリックでピン）
  - なぞる → ふつうにスクロール（`touch-action: pan-x pan-y`）
  - **長押し（450ms）で選択が始まる**（対応端末は短く振動）→ そのまま指を動かすと範囲、動かさずに離すとその場にピン。長押しの前に 10px 以上動いたらスクロールとして扱う。選択中は `touchmove` の既定動作を止めてページを動かさない
  - 短いタップでは何も作らない（既存のピン・範囲を押すとそのスレッドが開く）
  - 長押しで出るブラウザのメニュー（画像の保存など）と文字選択は出さない（`contextmenu` の抑止、`-webkit-touch-callout: none`）
  - 指で操作する端末（`pointer: coarse`）では、コメントが無いときの案内を「長押しして、そのままなぞると範囲、離すとその場にコメントできます」に
- **バウンススクロール**: `overscroll-behavior-y: none` を全体に（`:where(html, body, *)`。詳細度 0 なので個別に上書きできる）。iOS のラバーバンドと Android の引っ張り、内側のスクロールが外側へ連鎖するのを止める。Android Chrome の「引っ張って再読み込み」も効かなくなる。横は戻る操作のジェスチャーがあるので触らない
  - **2026-10-15 修正（利用者指摘「ホームを編集の中でスクロールができない」）**: 全要素（`*`）に付けていたため、M3E のリスト（`m3e-list` の本体は overflow: auto）や横スクロールの表のように「スクロール枠だが縦には動かない」要素にも付き、その上で指を動かすとスクロールが外側（ダイアログ・ページ）へ伝わらず止まっていた（PC のホイールは影響なし）。付ける先を、ページ全体（html・body）と画面の高さいっぱいの縦スクロール枠（紙面 `.viewer__stage`・引き出し `.drawer__body`・コメント一覧 `.comments__list`・文章 `.write__canvas`・投稿確認 `.post-review-wrap`）に絞った。ダイアログ・ボトムシートの中のスクロールは M3E の shadow DOM の中なので、もともとこの指定は届いていない
- 合わせて直した点: compact の版比較でビューアの浮遊ツールバーがはみ出していた → はみ出さず横スクロール（キーボードでも辿れるよう `tabindex=0`）。投稿欄はツールバーより手前に出す
- 撮影 26a（compact・受付中の版で、なぞるだけでは投稿欄が出ないこと、長押ししてなぞると範囲が描かれ投稿欄が出ることを、タッチの pointer イベントで検証）。実機の指では未確認

## 26. 画面の上下の縁（iPhone のセーフエリア）（2026-10-14・利用者指摘「下に色がつかないの嫌だ」「上が少しボケてる」）

- **下**: 下部ナビの色がホームインジケーターの下まで届かず、下地の色が帯になっていた。M3E の `m3e-nav-bar` は色を shadow の中で塗るので、セーフエリア分の `padding-bottom`（host）が透明だったのが原因。host にも同じ色（`--m3e-nav-bar-container-color`、既定は surface-container）を塗った
- **上**: 共通アプリバーがスクロールで流れ、iOS Safari が上端で本文をぼかしていた（スクロール端の効果）。アプリバーを `position: sticky; top: 0` で画面に貼り付け、上のセーフエリア（ノッチ・ダイナミックアイランド）分を `padding-top: env(safe-area-inset-top)` にしてバーの色（surface）で塗る。左右のセーフエリア（横向き）も余白に入れる
- アプリバーの高さを `--mf-appbar-h`（64 ＋ 上のセーフエリア）にまとめ、エディタなど画面の高さを計算している所はすべてこれを引く
- 確認: Chromium の safe-area 上書き（上 59・下 34。iPhone の値）でダッシュボードを撮り、下部ナビの色が下端まで、アプリバーがノッチの下から始まることを確かめた。実機は未確認

### スマホで文章に範囲コメント

- 以前: 選び終えた合図（mouseup）で投稿欄を出していたので、指で選択のつまみを動かしているあいだに欄が出たり、出なかったりした。欄は選んだ文字のすぐ下（幅 300 の浮遊）で、キーボードや指に隠れた

### メンション

- 投稿欄・返信欄で「@」に続けて名前を打つと、その制作物を見られる人（制作者・主管担当・校了権限者・有効な閲覧以上の ACL）の候補が出る（M3E list）。↑↓・Enter / Tab・Esc、押して選択

### 拡大縮小

- アプリ全体はピンチ・ダブルタップで拡大しない（`html, body { touch-action: pan-x pan-y }` と iOS の `gesturestart` 抑止。viewport の `user-scalable=no` は WCAG 1.4.4 の検査に掛かり iOS も無視するので使わない）
- 校正物（PDF・画像・文章）はビューアの中でピンチと拡大ボタンで拡大縮小（`usePinchZoom`。指の中点の下が動かないようスクロールを合わせる）。文章は本文だけを CSS `zoom` で拡大し、範囲コメントの位置の計算は変えない。PDF・画像の長押し選択は 2 本目の指が載ったらやめる

### 色

- テーマの variant を `expressive` から `vibrant` にした。`expressive` はこの種（#1b5fb4）で secondary / tertiary の色相を回し、選択中のナビ・トーナルボタン・ホバーなどに緑（secondary-container #cffbe3、tertiary #006d46）が出ていた。`vibrant` は主色が種の青に近いまま（#005ab3）、secondary も青の系統（#c4d0ff）
- 「要確認」などの注意は tertiary をやめ、固定の注意色（`--mf-warning`）に。成功・注意・重大は意味の色として固定のまま

- 見えている画面の中央に（`100dvh`。iOS の `100vh` はツールバーの分だけ大きく、下にずれていた）、セーフエリアも余白に。アプリのアイコン・名前・説明を中央揃えで縦に並べた

### 校正物だけのピンチ拡大

- **実際には一度も効いていなかった**: ピンチの処理を付ける要素を、最初の描画のときだけ ref で見ていた。校正画面は読み込みが終わってからビューアを描くので、その時点では要素が無く、何も付いていなかった。加えて Pointer Events で受けていたため、ブラウザが 2 本指をスクロールとして扱った時点で `pointercancel` になっていた
- 作り直し（`lib/usePinchZoom.ts`）: 要素は state で受ける。**タッチイベント（passive: false）で受け、2 本指になったら既定の動作を止める**。指を動かしている間は CSS の transform で拡大して見せるだけ（PDF を描き直さないので滑らか）、指を離したら倍率を確定して描き直し、指の中点の下にあった箇所が同じ位置に来るようにスクロールを合わせる。トラックパッドのピンチ（Ctrl＋ホイール）も同じ
- アプリ全体は従来どおり拡大しない（`touch-action: pan-x pan-y` と iOS の gesture イベントの抑止）。倍率はツールバーの数字と ＋／− にも出る。添付を切り替えたら幅に合わせた大きさに戻す
- 大きく拡大したとき、PDF の canvas が端末の上限（iOS は 1 枚 1,600 万画素前後）を超えないよう画素密度を下げる
- PDF・画像・テキストで、2 本指を広げると拡大することを確かめた（Chrome の CDP で 2 本指のタッチを送る）。E2E には 1 か所だけ（compact の PDF でピンチすると倍率が 2 倍以上になる）を足した

## 38. 制作物一覧を「局 › 担当」の入れ子に（2026-10-15・利用者決定）

- **スマホ（compact）**: M3E の expandable list item を局 › 担当で入れ子に（既定はすべて開く）。行は今までの 2 行のリスト
- **切り替え**: 状態のフィルタチップの右に M3E の segmented button「主管担当／制作担当」（URL の `by`。既定は主管担当）。担当が 1 件も無いときは切り替えも見出しの行も出さず、今までどおりの一覧

## 40. フィードバック（制作の議論のスレッド）と集計の書き出し（2026-10-15・利用者決定）

利用者の FB 制度案への回答: 「制作に関連する議論は校正システムで完結させたい。Slack のようなスレッド型の議論ができると良い」。決めてもらったこと: 制作物ごとに話題別のスレッドを何本でも／委員なら誰でも見て書ける（非公開の制作物は閲覧権限のある人だけ）／添付・投稿テンプレ・メンションと通知・リアクション／版とは別。

- **ナビ**: 「フィードバック」（アイコン forum）。compact の下部ナビは 5 項目までなので「管理」はアカウントのシートへ移し、ラベルは短い「FB」（1 項目 75px 前後で 2 行に折れるため。読み上げは正式名）
- **一覧**（`/feedback`）: M3 リスト。上に制作物（非公開なら添える）、題名、最後の投稿（名前: 抜粋）、右に時刻と件数。新しい投稿があったスレッドが上、未読は点と太字。「自分が関わる」のフィルタチップ、制作物で絞ったときは入力チップ（エディタのアプリバーの「この制作物のフィードバック」から来る）。「スレッドを立てる」は広い画面では filled ボタン、compact はアプリバーのアイコン
- **スレッド**（`/feedback/$threadId`）: Slack のメッセージ列のように、アバター・名前・時刻（編集済み）・テンプレの印・本文・添付・リアクションを古い順に並べ、下に返信の欄（スクロールしても下に止まる。compact は下部ナビの上）。開いたら既読。制作物を見られる人には「制作物を開く」
- **投稿欄**: @ でメンション（候補はその制作物の FB でメンションできる人）・「テンプレ」メニュー（制作者・初回／制作者・版更新／校正er。書き出しに入れ、投稿に印が付く）・添付（10 件まで。送るときに R2 へ上げ、検証済みになってから投稿）・Ctrl＋Enter で送信
- **添付の表示**: 画像はその場に縮小して並べ、押すと全画面のダイアログで大きく。PDF は「開く」（ブラウザの PDF 表示）とダウンロード、.ai などはダウンロードだけ。SVG はダウンロードだけ（スクリプトを持てるため）
- **リアクション**: 決まった絵文字（👍 🙏 👀 🎉 💡 ❤️）。付いているものはフィルタチップ（自分が付けたものは選択中）、行末の「リアクションを付ける」からメニュー
- **自分の投稿**: ⋮ から直す（本文だけ）・削除（「削除された投稿」として残り、添付は誰も読めなくなる）
- **通知**: 返信はスレッドの参加者と制作者へ、メンションは本人へ（ベルからスレッドを開く）
- **集計の書き出し**（管理 › 制作物 › 集計を書き出す。A-4）: 担当で絞り（局なら局の担当すべて）、制作物ごとに版の数・初回提出日・校了日・校了までの日数・コメント数（版ごと）・不採用と持ち越しの件数と理由・フィードバックのスレッドと投稿の数を CSV で手元に保存
- **下部ナビの高さ**: `--mf-navbar-h` を決め打ちの 80 から、下部ナビの実際の高さ（セーフエリアを除く）を測って入れるように変えた（実際は 68。文字の大きさで変わる）。ナビの上に置く FAB と返信欄の隙間がなくなる

## 41. 自己校了の独立確認は確認者本人の操作で（2026-10-15・PR #1 レビュー P1）

制作者＝校了権限者の制作物（D2・`ApprovalPolicy.allowSelfApproval = false`）で、校了ダイアログの「独立確認者」（人を選ぶ欄）は証跡にならないため廃止した。

- 確認は版ごと。新しい版を出した・確認者が制作者や校了権限者になった・閲覧権限を取り消された・再開した、のどれかで確認し直す
- 制作物の登録・編集では名称・区分の長さ（200・100 文字）を入力欄に設定（PR #1 レビュー P2。サーバーでも同じ上限）

## 45. 端末への通知（Web Push）とスマホのスレッドの下部ナビ（2026-10-15・利用者指示）

## 48. 制作物一覧の絞り込みと表の間・「M3 に表は無いのか」（2026-10-16・利用者指摘）

- **余白**: 状態のフィルタチップと「主管担当／制作担当」の行と、表との間が 8dp しかなかった（チップの下の余白だけ）。操作の行（`.works__controls`）の下を **16dp** にした（M3 の 4dp 刻みで、関連する部品のまとまりの間。data table の仕様の「表を操作する部品は表の直上」はそのまま）。スマホのリストも同じ間隔
- **M3 に表はあるか**: 無い。§31 で確かめたとおり m3.material.io の部品一覧に data table は無く、M3E（@m3e/web 2.10.1 の custom-elements も確認）にも table・data grid は無い。表の正式な仕様は Material 2 の data tables だけ
- **どうするのが正しいか**: M3 で表が要る画面は「M2 の data table の寸法・振る舞いを、M3 のトークン（色・文字・形）で組む」のが Google 自身の実装と同じやり方（Angular Material の mat-table と Flutter の DataTable は、M3 テーマでこの形になる。M3E の paginator なども Angular Material と同じ作り）。ただし表を使うのは「行どうしを列で見比べる」ときだけで、1 件ずつ探して開く一覧は M3 の Lists を使う
  - 制作物一覧は PC では締切・納期・状態を行どうしで見比べるので表（§31・§38 の data table）、スマホは見比べるより開く用途なので M3E のリスト（expandable list item の入れ子）。この分け方は変えない
  - 表の中で M3E を使える所は M3E にしている: 絞り込みは filter chip、切り替えは segmented button、ページ送りは paginator、切れた文字は tooltip、読み込みは linear progress、セルの選択肢は select
