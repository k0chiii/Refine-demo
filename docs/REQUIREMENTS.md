## 1. 業務の目的とAs-Is

### 1.1 校正・版・校了の定義

- **制作物（Work）**: 対外的に提示する文章・グラフィック・UI・映像等。制作物の目的・主管担当・制作担当・関係担当・制作者・校了権限者・納期を持つ。
- **版（Revision）**: 制作物の提出スナップショット。**第0版（ラフ／構想・方向性の確認）**と**第1版以降（通常版）**は異なる段階として扱い、前者は任意。ひとつの版に複数ファイル／参照URLを持てる。複数デザイン案は通常ひとつのファイルに含まれ、分岐版管理は行わない。
- **校正**: 校正者が観点を示して評価・指摘・質問・議論し、制作者が改善を進める活動。対面校正の結果も記録対象。
- **版の校正受付（Review window）**: その版に新しい指摘を受け付ける時間窓。**期限到来、または次の版の提出確定で受付終了する**。いずれの場合も未対応指摘は自動解消しない。
- **指摘（Comment / Issue）**: 特定の版・ファイル・箇所と結びつく内容。採否、対応状況、次版への引き継ぎを別属性で保持する。
- **校了（Final approval）**: 校了権限者（複数可。「校了とみなす人数」が宣言したとき）が、指定の最終版を委員会の成果物として外部に出して問題ないと明示的に判断すること。

### 1.2 As-Isの代表例（媒体・担当により変動）

1. 制作統括が制作物を集約し、担当・制作者・校了者・期限などを登録する。
2. 制作者が制作し、Notionなどで制作物IDを確かめて、提出フォームや外部ツールから版を提出する。
3. Slackに版更新通知・リマインドが流れ、校正者はDrive / Google Docs / Figma / frame.io / PDF等の外部リンクを開く。
4. 校正者が対象媒体で指摘し、制作者はコメントを追い、必要に応じて対面・Slackで議論する。
5. 制作者が修正して次版を提出。過去の指摘を再確認し、最終的に校了権限者が校了を判断する。

**維持したい利点**: 関係担当を横断する検索、軽快な提出、過去版の参照、媒体に適した範囲コメント。  
**解消したい課題**: 情報の分断、IDの手入力、通知の過不足、指摘と対応結果の不一致、複雑な権限、重いファイルの提出失敗、試験運用不足。

### 1.3 対象と例外

MF99の校正・校了指針では、基本的に**委員会外部の人が目にする制作物**を扱い、文書番号付きの公式文書、規則類、一部の企画対応制作物などに例外・別管理がある。**MF100の適用範囲は未承認**であるため、媒体・対象外理由・管理方式を分類できるモデルにする。未承認対象を自動で正式な校正フローへ取り込まない。

## 2. To-Beの業務フロー（ツール非依存）

```text
制作物の必要性と目的を定義
      │
      ▼
制作物登録・担当/制作/校正/校了者の確認
      │
      ▼
第0版（必要な作品のみ）／第1版以降を提出
（ラフ/通常版を明示、期限、見てほしい点）
      │
      ▼
版の校正受付 ───────▶ 対面・Figma・動画等での議論
      │                       │
      │                       └─ 合意/未解決を対象版に記録
      ▼
【期限到来 または 新版の提出確定】
第n版の新規校正受付を終了
      │   ※ 既存の指摘は消さない / 自動解決しない
      ▼
制作者が指摘を採否判断し、修正内容・保留理由を記録
      │
      ├─ 次版が必要 ──▶ 第n+1版の提出（指摘の引継ぎ） ─┐
      │                                              │
      │       ◀──────────────────────────────────────┘
      ▼
校了前の必須確認・未解決の重大指摘の確認
      │
      ▼
校了権限者が対象版を明示して校了を宣言
      │
      ▼
公開・納品／履歴保存（再開が必要なら理由付き）
```

**重要**: 校正受付終了、校正者が読んだか、指摘が解決したか、制作物が校了したかは**独立した状態**であり、相互に自動変換しない。

**新版確定の原子性**: 提出準備・ファイル転送中は旧版の受付を維持する。サーバーで新しい版が確定した際に限り、旧版を`superseded`として閉じる。確定失敗なら旧版の状態は変更しない。すでに期限で閉鎖済みの版は閉鎖状態を保つ。

### 2.1 役割と業務責任

| 役割               | やること                                                                                             | やってはいけないこと                                                                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 制作統括・主管担当 | 制作物の登録・管理、担当・期限設定、優先度調整                                                       | 校了権限がなければ校了できない                                                                                                                                               |
| 制作者             | 版を提出し、指摘の採否と処置理由を決める                                                             | 校正の受付期限を独断で閉じたり、必要な合議なしに自己校了しない                                                                                                               |
| 校正者             | 自分の割当・期限を把握し、指摘や議論をする                                                           | コメントをしただけで「対応完了」と扱わせない                                                                                                                                 |
| 専門確認者         | めい、写真、外国語、規則、デザイン等の所管事項を確認                                                 | 専門確認と最終校了を無条件に混同しない                                                                                                                                       |
| 校了権限者         | 対象版と確認内容を踏まえ、公開可否を最終宣言                                                         | 必須確認未達・重大未解決のガードを無断で回避しない                                                                                                                           |
| システム管理者     | 設定、障害対応、監査、復旧。**職責・ACL・所属によらず、すべての操作の権限を持つ**（2026-10-30 変更） | 権限を越えても業務の状態の規則（校了後の編集禁止、受付終了の版への提出禁止、校了とみなす人数、独立確認の独立性など）は越えない。旧: 「業務上の校了権限を当然には取得しない」 |

### 2.2 業務上の原則

1. **第0版はラフとして独立した段階**で、方向性・構成などのレビューに用いる。第1版以降とは画面表示・フィルタ・校正観点を区別する。0版は任意で、通常版を「第0版から始まる通算番号」にしない。**0版からの直接校了不可は初期の設計提案**（制度承認要）。
2. 対面レビューと外部ツールを排除しない。結論・未解決事項・対象版への参照を残せればよい。
3. 制作物／版／指摘／判断の正本と、コメントを行う外部媒体の役割を混同しない。
4. 写真・めい・外国語など、専門確認に必要な事前申告を記録し、対象者を割り当てられること。
5. 制作が中止・取下げ・回収対象化した場合も、過去の版・判断履歴を単に消さない。閲覧制限や保存期間のルールは別途決める。

### 2.3 版の系列（v1.1確定事項と設計上の前提）

```text
0版（ラフ）[任意] ──提出──▶ 0版レビュー ────┐
                                             ▼
                              1版（通常版）提出確定
                                             │
                        旧版の受付を同時に終了（提出失敗なら維持）
                                             ▼
                                  1版レビュー
                                             │
                                  2版（通常版）提出確定
                                             ▼
                                  2版レビュー → …
```

- **決定**：0版と通常版は別種別。通常版の番号は必ず1以上。0版は必要な作品にだけ存在する。
- **決定**：同時に新規校正を受け付ける版は制作物につき高々1件。新版提出確定が旧版を閉じる。
- **決定**：案A/Bのような分岐系列は用意しない。複数案は同一版のファイル内容として扱う。
- **実装上の仮置き**：0版は1制作物につき1件。0版の再提出を繰り返す運用や0版からの直接校了は、制度確認があるまで実装しない。

## 4. 画面・ユーザー体験

**U-01 自分の校正待ち**: 締切が近い順に、制作物、版、制作担当、用途、必要確認、未確認／確認済み、緊急度を表示。情報密度を保ち、検索・フィルタ・ソート。校正対象がゼロの理由も分かる。  
**U-02 制作物一覧**: 名称・旧ID・主管／制作／関連担当・媒体・校了状況で検索し、権限のない作品は一覧上にも表示しない。  
**U-03 制作物詳細**: 目的、対象者、担当、制作者、校了者、納期、現在版、履歴、未対応指摘、外部リンク、専門確認、活動履歴。  
**U-04 版提出**: 元の制作物から開き、自動的に対象を引き継ぐ。変更点、見てほしい観点、校正期限、公開対象ファイルを指定。巨大ファイルはアップロード状態と再送可能な範囲を表示。  
**U-05 校正ワークスペース**: 左にPDF/画像/文章、右にコメント。ページ・矩形・ピン等の位置とスレッドを双方向リンク。版、残り時間、校正対象者を常に確認できる。  
**U-06 指摘対応**: 制作者がコメントを種別／重大度／状態／担当で絞り、採用・不採用・保留・次版引き継ぎを理由付きで記録。  
**U-07 校了**: 校了版・必須確認・重大未解決件数・例外理由・実行者を最終確認して確定。二重クリック防止。  
**U-08 管理**: **作品ごとの閲覧許可をNogikuユーザー単位で追加・変更・剥奪**し、変更者・時刻を記録。専門確認ルール・通知・監査・障害を管理。グループからの自動権限付与は将来拡張。

**デザイン**: Material Design 3 Expressiveは画面の階層・操作強調・状態表現で使用する。校正用テーブルの情報密度、キーボード操作、アクセシビリティを犠牲にしない。`@m3e/react`はコミュニティ実装なので必要コンポーネントの実在・API・保守性をPoCで確認し、不足分はトークンに合わせて補完する。

## 5. 状態管理の不変条件

### 5.1 独立する状態

```text
Work.lifecycle       draft / active / on_hold / finalized / cancelled
Revision.review      scheduled / open / closed / void
ReviewAssignment     pending / viewed / responded / excused
Comment.resolution   open / acknowledged / accepted / rejected / deferred / resolved
Approval             none / completed / revoked (履歴イベントを保持)
Revision.kind        rough(0版) / standard(第1版以降)
```

_注_: 列挙値は**設計提案**。確定の前に制度担当と照合する。`accepted`は「反映すると判断した」ことであり、`resolved`は「反映済みなど確認された」ことである。単一の「校正済」フラグへ統合しない。

### 5.2 厳守すべき制約

1. 版の受付期限を `deadlineAt` のタイムスタンプ（内部UTC、表示Asia/Tokyo）で保持する。新規指摘は **`now < deadlineAt`** かつ**当該制作物の最新の受付対象版**である場合にのみ可能。表示上の期限閉鎖ジョブが遅れても、バックエンドの比較で拒否する。
2. **新版の提出が確定したら、旧版の受付を即時終了**し、その版への**新規指摘**を止める。既存指摘への制作者の採否判断・対応記録は残す（期限後・新版提出後の返信可否は§12 D5で別途決定）。
3. 受付期限到来・新版提出確定はWorkを`finalized`にしない。レビュー担当者を勝手に「確認済」にしない。指摘を勝手に「解決済」にしない。
4. 校了を確定するには、ログイン本人、対象制作物、校了権限、必須確認、最終版が一致し、重大未解決がないこと。ただし、許可された例外処理では理由と所定の事前確認を残す。
5. 校了確定後、版提出や校正指摘などの編集は通常禁止。再開する場合は別の監査イベントを追記し、過去の校了を消さない。
6. 版番号は制作物内で一意。**ラフは`kind=rough, sequence=0`、通常版は`kind=standard, sequence>=1`**。この二つを混在する連番として数えない。複数案のための枝番号は設けない。すでに確定した版のファイルを無言で差し替えない。誤提出の訂正は履歴を持つ。
7. `requestId` / 冪等キー、楽観的排他条件などにより、二重投稿・二重校了・二重版生成・Webhook重複通知を防ぐ。
8. PDF/画像上の座標はプレビュー表示の拡大率に依存しない。PDFはページ番号＋正規化座標、画像は原画像基準の正規化座標。原版のアンカーは後の差し替えで破壊しない。
9. 指摘の原文、投稿者、投稿日時、対象版と位置、処置履歴は監査可能にする。内容修正は編集履歴を残すか、原文・訂正記録を別に持つ。
10. 版の存在・コメント数・検索結果・添付URL・通知本文など、**非公開作品の存在を漏らすメタ情報も認可対象**。署名付きURLだけで認可を代替しない。
11. 新版の提出確定と旧版の受付終了は、**同じ業務上の一貫した状態遷移**として確定する。ファイルの転送準備・失敗・未検証の状態では旧版を終了しない。競合する同時提出を一件だけ確定する。
12. **閲覧ACLの作成・変更・取消は校正システム管理者だけが実施でき、本人認証・対象権限検証・監査記録が必要**。許可されない作品は検索・一覧・添付も拒否する。システム管理者は職責・ACL・所属によらず、すべての操作の権限を持つ（2026-10-30 変更。旧: 「管理権限は業務の校了権限を意味しない」。利用者決定 2026-10-30、DECISIONS）。

## 7. 認証・認可

### 7.1 既存実績の利用

- **Nogiku Auth**: OIDCでSSOするIdP。独自パスワードを作らない。
- **Nogiku Access**: 局・担当・役職などの権限を提供する既存の組織情報源。**組織グループを作品権限へ自動反映する機能は後続**。Nogiku AuthによるSSOは初期から使用。
- **MF99 UniQ**: NogikuとConvexを連携した実証済み実装。実際の認証クライアント・JWT・権限判定を確認して再利用する。
- **MF100**: 初期はNogikuユーザーを特定して、制作物単位の個人ACL・職責（制作者、校了者等）による権限を評価する。校正システム管理者が閲覧者を追加・除外できる管理画面を設ける。
- **将来**: Nogiku Accessのグループ・役職を権限主体として利用できる設計にし、同期や失効伝播、手動ACLとの優先順位を改めて決定する。

### 7.2 操作権限の最小モデル

| 操作                   | 主に許可されるロール                             | 例外／注意                                                                                                                            |
| ---------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| 制作物一覧・詳細       | サインインした委員（105A）                       | ACL は校正・編集・管理の委任用。閲覧は全員                                                                                            |
| 制作物登録・変更       | 主管／制作統括                                   | 登録と「有効化・正式校正開始」は別概念とする案                                                                                        |
| 版提出                 | その作品の制作者／委任された担当                 | 受付・校了・中止状態で制限                                                                                                            |
| 新規指摘               | 割り当てられた校正者・専門確認者等               | 版ごとの受付期限で制限                                                                                                                |

## 9. コメント・媒体別の詳細

### 9.1 PDF / 画像

- PDFにはページ番号・正規化矩形／ピンを保存。ズーム、ページ回転、異なるビューポート幅でも位置が変わらない。
- 画像は元画像に対する座標を0〜1へ正規化。画像のトリミング・表示枠と注釈位置を独立させる。
- スレッドの種別: `correction`（修正提案）, `question`（質問）, `discussion`（議論）, `decision`（対面等の合意内容）。重大度は独立属性。分類は設計案。
- 同じ版に複数ファイルがあっても、アンカーが対象ファイルを取り違えない。
- 署名付きファイル閲覧URLは短命で、権限剥奪後に新たなURLを発行しない。キャッシュ・CDNも考慮。

### 9.2 文章

- 初期は版の固定スナップショットと範囲コメントを重視。Google Docs並みのリアルタイム共同編集は**未決・後続**。
- 既存`notation`の正規表現・表記辞書の再利用を検討。辞書には年度・言語・利用用途・ルール版・例外を持たせる。
- **ルール検査**と**LLM提案**は分ける。置換候補を自動反映しない。正表記自身を誤検知する・ルールが重なった場合の挙動をテストする。
- 文書位置の安定性が必要なため、範囲コメントは確定した版のスナップショットに結び付ける。

### 9.3 外部媒体

- Figma、frame.io、サイトURL、対面打ち合わせ等の**媒体固有の議論の場**は残せる。
- 各版に外部URLと校正結果（判断概要・未解決点・確認者・日時）を登録できる。
- 外部コメントを完全同期したと誤認させない。取得不可・同期外の状態を明示する。

## 10. 通知と期限

1. アプリ内の「自分の確認待ち」と版の状態が正本。Slackは補助通知であり、通知が届かなくても業務履歴が失われない。
2. 版提出、明示メンション、期限が近い未確認、重要な判断依頼、校了などに限定した通知を優先する。
3. リマインドは担当・本人の必要性に応じて制御。何度も同じ内容を送らない。MF99調査では21人中、校正リマインドが「多い」10人、必要19人。
4. 通知成功≠相手の既読≠レビュー完了。送信失敗時はジョブ再試行し、業務データはロールバックしない。
5. 期限はAsia/Tokyo表示、バックエンドではタイムスタンプで判定。タイムゾーン・日付のみ入力の場合の具体的締切時刻をUIで必ず明示する。期限延長・取消・緊急案件のルールは承認待ち。

## 13. 品質・運用・非機能

- **セキュリティ**: Nogikuで認証し全てのサーバーアクションで対象認可。隠しURLを権限制御代わりにしない。署名付きR2 URLは短命、対象ファイルの権限を検査。
- **可観測性**: 認証失敗、アップロード失敗、期限ジョブ、Webhook再試行、通知失敗、重要監査イベントを追跡。機微情報をログへ丸ごと流さない。
- **データ保全**: DB・R2の整合したバックアップと復元試験。辞書・設定・索引再構築手順も管理。具体的RPO/RTOは合意待ち。
- **性能**: 制作物・版・コメント数の増加に耐えるインデックス、遅延読込・ページング。大容量PDF/画像でも画面全体をブロックしない。
- **アクセシビリティ**: キーボード、フォーカス可視、スクリーンリーダー、コントラスト、アニメーション低減（reduced motion）。M3E演出より仕事の可読性を優先。
- **年度交代**: 権限見直し、鍵の交換・破棄、データエクスポート、システム所有者、監視・復元手順の引き継ぎ。
- **低利用期**: 6月〜10月は重いバッチ・LLM処理・不要な通知を停止または抑制し、保管と安全な閲覧・復旧能力を維持。休眠状態への切替はデータ復旧要件を満たす場合のみ。
- **外部データ**: 将来LLMにコメントや制作物を送る場合は、送信先・機微情報・保存条件・承認を設計し、明示的な権限なしに自動送信しない。

## 14. 実装の分割と着手手順（Claudeへ）

### Phase 0：調査と設計の土台

1. 既存repoが指定されたら**最初に読み込み、破壊的な初期化をしない**。まだ無ければモノレポ／単一リポジトリを提案する。
2. UniQで実証済みのNogiku→Convex連携コードと、既存Nogiku SDKの実際の利用方法を確認する。**未確認のAPIを捏造しない**。
3. `docs/DECISIONS.md`にD1〜D15を記載し、**D1決定・D4延期・D2/D3要承認**の現在値を明記する。
4. データモデル図、制作物・版・コメント・校了の独立状態遷移、認可境界を文章と図で提出する。
5. 認可テストと期限・校了・冪等性のユニットテストを先に設計する。

### Phase 1：縦に一周するMVP

1. React/Vite/TanStack Router/M3Eで、制作物一覧・詳細・版提出の画面枠を作る。
2. ConvexにWork/Revision/Artifact/Comment/Approval/Auditと**作品単位ACL**を実装し、サーバー上の認可・状態ガードを実装する。
3. Hono WorkersにR2提出と短命アクセスURLの発行を実装する。業務CRUDはConvex経由に一元化。
4. PDF・画像の注釈UI、コメント／指摘処置、レビュー割当と校正待ちダッシュボードを実装する。
5. 校了と再開、重大未解決ガード、監査、同時操作と権限テストを実装する。
6. 代表作品を使って、**0版（任意）→1版→指摘→2版提出確定と1版受付終了→指摘処置→校了**をE2Eで検証する。提出失敗と権限変更も検証する。

### Phase 2：現場運用向け補強

- Slack通知とエラーハンドリング、専門確認、文章の範囲指摘とnotation、バックアップと復元、アクセシビリティ、性能測定、委員への案内。**過去データ移行は本フェーズにも含めず別途将来判断**。
- AIの持越候補、共同編集、外部コメント同期、**Nogiku Accessグループ連動**などは必要性が確認されてから。

### Claudeに期待する成果物

- `README.md`: 開発起動、環境変数の名称、権限・デプロイ概念、検証方法。
- `docs/REQUIREMENTS.md`: 本書（改変するなら差分を明記）。
- `docs/DECISIONS.md`: D1〜D15の決定ログ。未決定を未決定のまま表示。
- `docs/ARCHITECTURE.md`: コンポーネント図と認可・ファイルフロー。
- `docs/TEST_PLAN.md`: A-01〜A-20に対応するテスト一覧。
- 実装ソース、型定義、データスキーマ、ユニット／E2Eテスト、サンプルデータ生成スクリプト。
- 動くローカルMVPと、できていない点・実行していない試験を区別した引き継ぎメモ。

### やってはいけないこと

- 既存repoやUniQの認証コードを見ずに、Nogiku認証を適当に自作する。
- 委員のSSOと同じ資格情報をもう一つのユーザーDB・パスワードDBに複製する。
- 受付期限と校了を一つの`completed`フラグにまとめる。
- 重大未解決の校了ガードをフロント画面の警告だけで済ませる。
- PDF/画像・コメントを公開バケットで無制限に配信する。
- Claude独自判断で本番環境にデプロイ、課金、現行データ削除、既存システム変更、外部LLMへの実データ送信をする。
- 高額な外部有料コンポーネントを事前承認なく採用する。
