# 利用コストの見直し（Convex / R2 / Workers / Pages）

利用者指示（2026-10-18）「R2 や Convex などの使用コストを最大限に効率化し、エッジコンピューティングと Convex を最大限に活用できるように見直して欲しい」への対応記録。
**画面・文言・読み込み中の表示・認可・ファイルのキャッシュ方針（`Cache-Control: private, no-store`）は変えていない。** 変えたのは「読む量・呼ぶ回数・取り直す量」だけ。

> 数字は**コードを読んで置いた前提からの見積り**で、本番の計測値ではない。金額は各サービスの単価・無料枠が変わるので、量（GB・回数）で示し、換算は契約中のプランの単価で行うこと。
> 効果の確かめ方は「7. 計測」。デプロイや課金の設定は行っていない（「6. デプロイとダッシュボード設定」は利用者が行う）。

## 0. 要約

- **コストの本体は Convex のデータベース帯域**（読み取ったドキュメントの量）。関数の呼び出し回数（月 30〜40 万回の見積り）や R2・Workers・Pages は、この規模では**無料枠の内側**で、金額はほぼゼロ。
- Convex の帯域を食うのは「**全制作物を読む常時購読の問い合わせが、どこかの書込みのたびに全員分やり直される**」こと。制作・校正・制作物の入口（`dashboard.get`。2026-10-19 にホームを入口に分けた。UI_M3E §83）、シェルに常駐する FAB の候補（`home.submitTargets`）、制作物一覧（`works.listMine`）が上位。
- 今回の変更で、通常月の見積りは**約 62GB → 約 20GB（−68%）**、締切週は**約 133GB → 約 41GB（−69%）**（2.2 の前提。主に `home.submitTargets` が 2.0MB → 0.47MB / 実行、ダッシュボードが 3.5MB → 1.85MB / 実行）。R2 の読み取り操作（Class B）は**約 −47%**、Convex への認可の問い合わせは**約 −40%**（重なって届く分）。
- **残る最大の山はダッシュボードと制作物一覧の「全制作物を毎回集計する」作りそのもの**。ここは非正規化（制作物ごとの要約・カウンタ）が要り、データの埋め直し（バックフィル）と UI の分割を伴うので、今回は設計だけ示して見送った（「5. 残りの推奨」1・2）。

### 2.3 Convex: 関数の種類・cron

- **action は少ない**: `ai.proofread`（利用者が確認して押したときだけ。`apps/convex/convex/ai.ts:106`）と `pushNode.deliver`（端末を登録した人への通知のときだけ）の 2 つ。mutation や query で足りるものを action にしている箇所はない。
- **cron**（`apps/convex/convex/crons.ts:9-15`）: 受付終了を 1 分ごと（月 4.3 万回）、リマインド・放置セッション・放置添付を毎時（月 約 2,200 回）。受付終了の 1 分は**表示のため**に要る（期限の判定自体は各 mutation の時刻比較で保証されるが、`revisions.get` は読み取りで時刻を読むため、受付終了の印は cron の書込みで購読を再実行させて反映している）。索引の範囲が空なら読み取りも書込みもほぼ無いので、止めない。呼び出し回数は月 4.6 万回で、この規模の 0.2% 未満。
- **大きな文書**: ファイル本体は R2 にあり Convex には入れていない。文章の下書き（`documentDrafts`）は本文を 2 重に（JSON と平文）持つが、書く人が限られ、量は小さい。
- **ページネーション**: 一覧は上限つきの `take`（`listMyWorks` は 2,000 件、通知は 20 件）で、`.collect()` で無制限に読むのは `by_revision` / `by_work` のような**親で絞った小さな集合**と、表記統一のカテゴリ・ルール（400 件程度。今回、必要なカテゴリだけに絞った）だけ。
- **使われていない問い合わせ**: `reviews.myQueue` は Web から呼ばれていなかったので消した（推奨 10）。

### 2.4 R2

- 操作の内訳（月）: Class A（PUT）は版の提出のたびに数回で数百回。清掃の削除は無料。**Class B が主**（GET / HEAD）で、PDF の初回 1 回あたり 31 回（本体 1 ＋範囲 15 本 × HEAD と GET）だったものが 16 回になった（3.2）。
- 転送は Worker 経由でも **egress 無料**。署名付き URL を出さない方針（A-11）のままで、R2 への課金は増えない。
- マルチパートアップロードは**使っていない**（Worker が `put` 1 回で受ける）。放置された未完了のマルチパートは存在しない。Worker のリクエスト本文の上限（100MB）を超えるファイルが要るようになったら、マルチパート＋「未完了を中止」のライフサイクルが要る。
- 孤立オブジェクトの清掃は既にある: 放置セッション（毎時 Convex が `abandoned` にし、Worker の cron `23 * * * *` が R2 から消して `purgedAt` を記録）、採用されなかった試行（`listOrphanCandidates`）。**R2 側のライフサイクルルールは不要**（キーを Convex が全部把握している）。
- **可逆な圧縮による保存量の削減**（利用者指示 2026-10-19「劣化ゼロだけ」。[`DECISIONS.md`](DECISIONS.md)）: ダウンロード専用の原本（`.psd`・`.indd`・`.eps`・`.tif` など、256 KB 以上で 10% 以上縮むもの）は gzip のまま R2 に置く。これらは圧縮前の形式が多く、数十 MB 級のファイルで保存量が 2〜5 割ほど減る見込み（形式と中身による。PDF・JPEG・動画は元のまま）。PNG もブラウザで可逆に作り直してから上げるので、色数の少ない画面の PNG は半分以下になる。無料枠（保存 10GB）の内側のままなので金額は動かないが、保存量の伸びが遅くなる。増える操作は、圧縮して上げたファイル 1 件あたり **Class B が 1 回**（Worker が置いた直後に読み戻して伸長・SHA-256 を確かめる）と、その配信で Range が使えず**範囲取得が全体の取得 1 回になる**こと（ダウンロード専用なので使うのは保存のときの 1 回だけ）。egress は無料のまま。
- サムネイルなどの派生物は作っていない（再生成のコストなし）。制作物の削除機能が無く（取消は状態だけ）、版の無効化でも実体は残す（監査）。

### 2.5 Workers（エッジ）

- `GET /files/:id` は 1 リクエストごとに Convex の `artifacts.authorizeAccess`（読み取り 4〜5 件）を呼ぶ。PDF.js の範囲取得で 1 ファイルが十数本になるため、**Convex の呼び出しの最大の発生源は Worker**（月 約 17 万回）。
- JWT の検証は isolate で使い回し済み（前回の変更）。CPU は軽い。
- Smart Placement は未設定。

### 2.6 Pages / PWA

- `_headers`: `/assets/*` は `immutable`、`index.html`・`sw.js`・マニフェストは `no-cache`（既存）。**ハッシュの付かない `/pdfjs/*`・`/ocr/*`・`/devices/*`・`/icons/*` は指定が無く**、Pages の既定（`max-age=0, must-revalidate`）で開くたびに確認の往復をしていた。
- Service Worker の先読みは 256 ファイル・約 6.5MB（圧縮前）。**新しい版が出るたびに全部を取り直していた**（`cache: "reload"`）。

## 4. 見送ったこと（理由）

- **認可の判定を一定時間（数秒でも）キャッシュする／最初の認可のあとに短命の署名トークンで範囲取得を通す**: 採らない。どちらも「権限剥奪後の**次の要求から**読めない」（要件 §9.1 / A-11）を TTL の分だけ弱める。署名トークンは秘密の管理と、トークンが漏れたときに別の添付・別の利用者に使えないことの証明も要る。一方で得るものは Convex の認可の問い合わせ（読み取り 4〜5 件・月 10〜17 万回）の削減で、**無料枠の 1% 台**。割に合わない。代わりに「同時に届いた同じ問い合わせを 1 本にまとめる」（終わった結果は残さない）だけを入れた。
- **`Cache-Control` を公開キャッシュ可にする／Cloudflare のキャッシュ（`cf.cacheEverything` や Cache API）に認可つきのファイルを載せる**: 採らない（A-11。前回の変更と同じ）。
- **Smart Placement**（`placement: { mode: "smart" }`）: 入れない。Worker が R2（エッジ側）と Convex（リージョン固定）の両方を呼ぶため、効くかは実測しないと分からず、効かなければ利用者から遠い場所で動いて遅くなる。試すなら先にステージング環境で、Workers の「Placement」の指標と TTFB（p50）を見る（6 を参照）。
- **PDF の範囲取得の単位（64KB）を大きくする**: 範囲取得の本数が減る（約 15 → 約 4）が、離れた箇所を読む PDF では運ぶバイトが増える。実際の PDF で計測してから（前回の変更で既定のまま残した理由と同じ）。
- **Worker の cron（毎時）や Convex の cron を間引く**: 呼び出しは月数百〜数万回で、無料枠の 1% 未満。孤立した実体の滞留が長くなるだけなので、やらない。
- **通知のバッジの数を非正規化したカウンタにする**: バッジの問い合わせは未読の索引を最大 100 件読むだけで小さい。カウンタを足すと、既存の通知の埋め直しと全書込み経路の変更が要るのに対し、得るものが小さい。
- **文章・SNS の自動保存の間隔を伸ばす**: 1.2〜1.5 秒の「入力が止まってから」の保存で、書く人が限られ、量は小さい。伸ばすと「保存済み」の表示が遅れ、書きかけを失う窓も広がる（UI の挙動を変える）。
- **`workRoles`（職責の派生表）で `home.submitTargets` を引く**: 全制作物の読み取りが 0.47MB → 数 KB になる大きな効果があるが、本番のデータで同期が取れているかを確かめる（最悪は埋め直し）必要がある。確認できないので見送り（推奨 4）。
- **使われていない索引の削除**（`by_lifecycle`・`by_principal`・`by_work_state`・`by_submitter`・`by_revision_resolution`・`by_assignee_state`・`by_parent`・`by_uploader`、検索索引 `search_title`）: 今後使う予定の索引かを判断できないので、`by_post`（今回の索引で置き換えたもの）以外は残した（推奨 6）。
