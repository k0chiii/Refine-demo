SECTION 01

確定条件・提案・未決事項

以下を同じレベルで「仕様確定」と呼ばない。設計レビュー時の前提を最初に共有する。

分類 内容 根拠・検討
利用者決定 版の校正受付は期日で終了。制作物全体は権限者一人が校了を宣言。 本対話で確認。
利用者決定 PDF・画像注釈を内製。文章も内部で完結する方向。動画・Webは外部を許容。 本対話で確認。
利用者決定 制作物情報の正本は新システム。重要未解決指摘がある校了は原則禁止、理由付き例外。 本対話で確認。
利用者決定 フロント／バックエンドはReact + M3E + Convex + Hono + R2 + Nogikuを第一候補。繁忙期11〜5月。 本対話で合意した設計方針。
既存実績 UniQでNogikuとConvex連携、Convex自己運用の経験がある。 MF99 UniQ資料と利用者の補足。
設計提案 AIが前版の未解決指摘を候補として次版へ結び、制作者が承認。 誤転記防止と追跡性のため。
要決定 対象範囲、詳細RBAC、同時に受付可能な版数、権限失効、媒体ごとの必須確認項目。 関係担当との合意が必要。
SECTION 02

目指すサービスと対象範囲

業務To-Beを満たすことが目的。常に全てを同一UIに収めることは目標にしない。

MVP内

  • 制作物・版・関係担当・期限の正本
  • 校正待ちダッシュボード、権限・検索・通知
  • PDF・画像の位置指定コメント、スレッド
  • 版受付の自動期限終了、追跡可能な判断
  • 校了宣言、理由付き例外、監査履歴
  • 文章の表記ルール検査と限定的な編集

当初は外部・後続

  • 動画の時間軸・フレームへのネイティブ注釈
  • Webサイト全体のDOM／画面注釈自動追跡
  • Adobe編集機能そのもの
  • AIによる校了可否の最終判断
  • Webや映像の全コメントを自動で双方向同期
  • ゼロからの独立したID／権限基盤
非機能上の前提： 委員会内の年間運用。11月〜5月に利用が集中し、6月〜10月も閲覧・監査・バックアップと引き継ぎを妨げない。
SECTION 03

ドメインと境界

「制作物」「版」「校正受付」「指摘」「校了」は別の概念・別の集約として扱う。

Work

制作物

目的・媒体・主管・制作担当・関係担当・担当者・校了者・納期・ライフサイクル。

Revision / ReviewWindow

版と受付期間

版番号・提出者・提出時刻・期限・公開対象と関連ファイル。各版の受付状況。

CommentThread / Decision

指摘と判断

指摘の原文・場所・分類・反映可否・持ち越し・最終判断の記録。

MF99の校了指針は、公開可否を権限者が判断すると定める。MF100でもコメント件数や締切だけから「校了」を自動的に推測しない。根拠
SECTION 04

状態機械と禁止事項

まず禁止遷移を言語化する。UIだけでなくサーバー側の不変条件として実装する。

イベント／遷移 条件 システムの処理
submitRevision 制作物がactive、提出権限あり。必要メタデータと実体ファイル確認。 版を確定し校正受付開始。必要担当へ依頼。
deadlineReached 受付期限を経過。 該当Revisionのみclosed。未読・未解決は変更しない。
recordDecision 担当する制作者・委任者。コメントが対象版に紐づく。 採用・非採用・次版持越などの判断を追記。
finalizeWork 校了権限あり、必須確認と公開版あり。 校了者・確定版・日時・例外理由を記録し版更新停止。
reopenWork 例外権限、理由を必須。 校了履歴を維持し再開イベントを追記。
未決事項：提出後に次版が開かれる前に、前版の期限を待つか、早期終了するか。推奨は同一制作物につき受付中の版は原則1つとし、早期終了には理由を必須にする。
SECTION 05

業務ユースケースと受け入れ基準

MVPで最低限、利用者が迷わず通れるべき経路を定義する。

ID / 操作者 操作と期待結果 受け入れ条件（抜粋）
UC-01
制作統括		 制作物を登録・検索・修正する。 制作物名・担当から検索可。重複登録・無効な状態を明示。
UC-02
制作者		 ファイルと説明を用いて新しい版を提出する。 アップロード失敗時に何を再送するか明示。ファイル検証前に公開しない。
UC-03
校正者		 校正待ちを確認し、位置指定で指摘する。 対象版・期限・担当が常に表示。未読と確認済みを区別。
UC-04
制作者		 指摘を採否判断し、反映結果を次版で示す。 却下・持越には理由を残す。元版の履歴は消えない。
UC-05
システム		 版ごとの校正期限を適用する。 期日を過ぎると新規コメント受付停止。作品の校了は行わない。
UC-06
校了権限者		 最終版に校了を宣言する。 重要未解決は警告。例外時は理由・確認操作・監査ログ必須。
UC-07
関係者		 対面校正の結論・外部リンクを記録する。 関係者と日時、元版への参照を残せる。

SECTION 07

認証・認可：NogikuをSSOの正本にする

UniQでのNogiku×Convex連携を実証済み資産として扱い、まずは実装を確認・再利用する。

Nogiku AuthOIDC / 委員SSO / ID
→
MF100 セッションConvex / Honoで利用
→
MF100 の権限確認Nogiku Access + 制作物固有権限

認証の役割

  • ログイン・本人識別：Nogiku Auth。
  • 局・担当など組織上の権限：Nogiku Access。
  • 「この制作物の版を更新／校了できるか」：MF100側で対象との関係も検証。

検証する境界

  • UniQが使っているOIDCクライアント・署名検証方式。
  • Convex FunctionとHono APIの権限判定結果を一致させる方法。
  • 権限変更・役員交代時の失効／再ログインの条件。
  • 制作者本人と校了者が同じ場合の合議ルール。
ブラウザによる「ボタン非表示」だけで認可を済ませない。署名付きURLの発行とコメント・校了操作を、それぞれサーバー側で検証する。

一次資料：UniQ ／ Nogikuの構成と権限。

SECTION 08

採用するシステム構成（合意案）

リアルタイムの業務データをConvex、ファイルの転送・外部連携をHonoに分ける。DBを二重化しない。

担当領域 技術 責務と禁止事項
Web / PWA React 19, Vite, TanStack Router, @m3e/react 業務UI、PDF表示、ビューア、フィルタ。UIのみで権限を確定しない。
業務ロジック Convex トランザクション・リアルタイム購読・監査履歴の正本。
HTTP / ファイル Hono (Workers), Zod アップロード準備、署名、Webhook。ConvexとCRUDを重複実装しない。
保存 Cloudflare R2 原本、PDF、画像、プレビュー。アクセスは短命認可で制御。
認証 Nogiku Auth / Access 既存SSO・委員権限を利用。新しいパスワードDBを作らない。
文章 Tiptap / ProseMirror + notationルール 位置指定指摘と辞書検査。LLM判断を強制適用しない。
SECTION 09

校正UI：媒体別に必要な境界を設ける

統一するのは業務データ。コメントUIは媒体によって、表示・座標・編集権の仕様が変わる。

媒体 当初の校正UI コメントアンカーと注意点
PDF PDF.jsにSVG注釈レイヤー pageIndex、正規化座標、矩形範囲。ページ回転、縮尺、印刷・複数ページに対応。
画像 canvas/SVGでピン・矩形 画像座標は0〜1に正規化。表示領域と元サイズの違いを吸収。
文章 Tiptap / ProseMirror 範囲コメント、編集時位置追随。版確定時の文書スナップショット必須。
映像 外部（例：frame.io） 版と対象URLを管理。コメント自動同期は後続検討。
Web/UI 外部（例：Figma、対象URL、必要に応じPDF化） 0版・ラフと公開後の改修という性質差を扱う。
アンカー不変性：コメントの位置は対象版に固定。AIが次版の対応位置を推定しても、元の位置を上書きせず候補として追加する。
SECTION 10

自動チェックと版間の指摘引き継ぎ

定型ルールは再現可能な検査へ。LLMは不確実な判断の補助に限定し、履歴と責任を消さない。

既存資産

表記統一：notation

既存のスプシ・正規表現に基づく誤表記検出・置換提案がある。重複・正しい表記への誤検出が課題として挙げられている。

  1. ルールセットを年度・言語・担当用途で版管理。
  2. 対象テキストを確定的に検査。
  3. 問題箇所をハイライトし、候補と出典を提示。
  4. 人が置換／無視、必要なら理由を記録。
新機能提案

未解決コメント引き継ぎ

  1. 前版のopen / deferred等を候補取得。
  2. 前版と次版を比較し、対応箇所を提案。
  3. 制作者が引継ぎ／対象変更／見送りを承認。
  4. sourceThreadIdとの参照を持った新しい指摘・引継ぎレコードを作成。
  5. 提案と最終判断を監査・再現可能に保存。
AIが自動で正誤を判定して指摘を消す、無断でコメント本文を書き換える、校了を確定する、という動作はさせない。類似コメントの重複統合も原文を残す。

出典：notation ／ 改善要望 ／ 文章校正指針

SECTION 11

コマンド契約と一貫性

Convex mutationを業務ルールの境界にし、Honoはファイル・外部HTTPの境界に置く。

// Convexの業務コマンド例（概念、実装確定前） createWork({ title, ownerTeamId, category, approverId, ... }) submitRevision({ workId, manifest, reviewDeadlineAt, note, expectedVersion }) postComment({ revisionId, artifactId, anchor, kind, severity, text }) decideComment({ commentId, decision, reason, expectedVersion }) finalizeWork({ workId, revisionId, exceptionReason?, expectedVersion }) reopenWork({ workId, reason, expectedVersion }) // Hono APIの例（ファイル実体・外部連携） POST /api/uploads/initiate -> uploadId + multipart params POST /api/uploads/complete -> R2実在確認 + Convex確定処理 POST /api/webhooks/... -> 署名検証 + 冪等処理 GET /api/files/:id -> 権限確認 + 短命なダウンロードURL

必須ガード

  • ユーザー／対象制作物の認可
  • expectedVersionで競合検知
  • 期限超過・校了済み時の書込み禁止
  • R2アップロード完了確認と孤立ファイル清掃

一度だけ実行したように扱う

  • requestId / idempotencyKeyを保存
  • 通知送信失敗を業務更新の失敗に見せない
  • 外部サービスをまたぐ操作を再試行可能に
  • 監査イベントを追記型で残す
SECTION 12

通知・権限・業務の例外

必要な人に必要な出来事だけ知らせる。投稿成功を、相手の既読・確認完了とみなさない。

出来事 通知先（案） 方針
版提出 その版の校正対象者 一覧を正本とし、Slack等は通知手段。多重通知を避ける。
コメント・返信 制作者・当該スレッドの参加者 必要に応じ即時通知。議論と修正を区別。
期限接近 未確認者のうち必要な人 本人／担当の方針で頻度調整。すでに対応済みなら再通知しない。
専門確認が必要 対象の専門確認者 めい・写真・言語など必要な確認を漏れなく振り分ける。
校了・例外校了 関係者、必要な管理者 確定版と判断者・例外有無を明示。
機密性の高い回収対象では、通知タイトルやファイル名自体が情報漏えいになり得る。見せてよい内容だけを通知本文に含める。

調査根拠：21人アンケート ／ MF99通知の振り返り

SECTION 13

非機能要件・検証項目

実装前に性能指標とテストデータを合意する。厳密な数値は実測前に断定しない。

観点 要件・評価方法 受け入れ基準の案
検索・一覧 制作物数、版数、コメント数が増えても必要な件数のみ取得。索引とページング。 繁忙期の端末環境でp95応答時間を計測し、合意した閾値以内。
同時利用 複数の校正者が同じ版へ投稿・更新。 重複・取りこぼし・他ユーザーの書込み上書きがない。
ファイル提出 大容量、複数ファイル、通信断、再試行。 失敗の原因を示し、途中復帰または安全な再提出が可能。
アクセス管理 校了・回収物・期限後書込み・権限剥奪。 サーバー側の認可試験と境界テストに成功。
復旧 Convex状態とR2ファイルを整合した世代で復旧。 バックアップからの復元試験を定期実施。
可観測性 エラー、ジョブ失敗、Webhook再試行、通知未達を記録。 利用者が操作失敗を判別でき、担当者が原因追跡できる。
量の試算：仮定として制作物数 N、平均6版、各版5名×10コメントなら、コメント数は N×300。例：N=600なら18万件。実測した制作物数・添付容量とは別に扱う。
SECTION 14

移行・試験運用・引き継ぎ

切り替えが遅れて二重運用になることを避ける。まず現行の業務とデータの正しさを保証する。

Phase 0

制度合意

PR・EVE・Web・校了者とフロー確認。媒体別に代表的な案件を選定。

Phase 1

小さく試す

校正待ち、版更新、指摘、期限終了、校了を縦に一周。

Phase 2

移行・並行確認

制作物と版のID対応、移行後照合、旧システム閲覧・更新停止。

Phase 3

委員会運用

通知、回収、文章・LLM、運用監視、年度引き継ぎ。

MF99振り返りでは、EVE合宿の開始までに導入できず、Slackで版更新が始まったという記録がある。実機テストを設計工程の末尾へ追いやらない。出典
SECTION 15

友人・関係者と決めたい論点

技術的に実装可能であっても、運用ルールの未決事項をコードで勝手に確定させない。

優先 論点 選択肢／検討材料
P0 1制作物に受付中の版を同時に複数許すか 原則1つ／媒体やラフは例外。次版提出時の旧版早期終了。
P0 校了の自己承認と合議 単独宣言を認める条件／同じ人が制作者の場合の牽制。
P0 資料移行範囲 全履歴移行／稼働中＋参照のみ／新年度データのみ。
P0 回収・非公開案件の閲覧範囲 漏えい防止のため、一覧／通知／添付それぞれ定義。
P1 文章の共同編集レベル 校正文書の編集まで内製するか、版の固定スナップショット中心か。
P1 AI引き継ぎ 人が承認する前提で、提案精度・確認コストを評価。
P1 Convex稼働場所 UniQセルフホスト実績の再利用可能性と、Cloud Starterの運用負担。
P1 稼働開始と二重運用停止 現場の制作スケジュールに合わせて段階切替。
