### C. 表記統一

| 機能                    | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ルールのモデル          | `ruleId`・カテゴリ・題名・説明・統一表記・誤表記・正規表現・例外（語句／直前／直後／カテゴリ）・言語（ja/en/zh）・適用範囲・年度・優先度・厳格さ（必須／推奨／要確認）・有効・版・作成更新者と日時・公開日時                                                                                                                                                                                                                                |
| カテゴリ                | A1/A2/A3/B/C/D/E。B・C・D は A1〜A3 を継承（変更可能）。用途に近いカテゴリが優先、カテゴリ例外、E は必須と推奨を区別。運用メモ（ルールにできない説明行）を持つ                                                                                                                                                                                                                                                                              |
| 年度                    | ルールに年度を付け、MF99 のルールを MF100 に無条件で当てない（取り込み時は年度を付ける）                                                                                                                                                                                                                                                                                                                                                    |
| 版                      | 変更のたびに版 +1、全版を履歴に保存（`ruleRevisions`）。校正結果はルール ID と版を記録                                                                                                                                                                                                                                                                                                                                                      |
| 制作物ごとの選択        | 登録・編集でカテゴリを人が選ぶ（プリセットあり。媒体・部署から自動では決めない）。提出時に「どのルールのどの版か」を版に記録（`revisions.notationSnapshot`）。後でルールを変えても過去の版の検査は変わらない                                                                                                                                                                                                                                |
| 管理画面（`/notation`） | 一覧・検索・カテゴリと年度の絞り込み・追加・編集・無効化・履歴・適用範囲・例外・CSV/JSON の取り込み（プレビュー: 説明行・警告・重複・矛盾）・書き出し（CSV/JSON。往復できる）・カテゴリ（継承・運用メモ・管理者）・試す                                                                                                                                                                                                                     |
| 権限（サーバーで判定）  | 一般: 閲覧・提案・報告 / カテゴリ管理者: 担当カテゴリの編集・承認 / システム管理者（または組織権限 `notation:manage`）: カテゴリ管理者の設定。Nogiku 連携は組織権限 `notation:manage`・`notation:category:<code>` を読むだけ（存在しない API は仮定しない）。Nogiku 未接続の `"*"` では管理権限を与えず、個人単位の設定で代替                                                                                                               |
| 提案                    | 管理画面から、または校正画面で選んだ文字から（選んだ文字・前後の文・制作物・版を自動入力）。承認・却下・編集して承認・まとめて処理。同じ提案は賛同としてまとめる。担当者へ通知、結果を提案者・賛同者へ通知。承認まで反映しない。元の制作物を見られない担当者には文脈を隠す。AI による自動のルール変更はしない                                                                                                                               |
| 検査エンジン（AI なし） | 辞書・正規表現・例外・優先順位・重なりの解決。行単位、一致数と時間の上限、危険な正規表現（長すぎる・入れ子の繰り返し）を拒否。「いただく／頂く」のような使い分けは「要確認」。結果: 元の文字・修正候補・位置・ルール・理由・例外・検出方式・信頼度                                                                                                                                                                                          |
| 文章エディタ            | 入力が止まって 800ms 後に Web Worker で検査、波線、表記パネル（修正・まとめて修正・無視・元に戻す）                                                                                                                                                                                                                                                                                                                                         |
| OCR                     | PDF.js の文字を優先し、文字の無いページ（20 ページまで）と画像は tesseract.js（日本語、学習データはアプリから配信）。位置付き、低信頼度は要確認。元ファイルは変更しない。縦書き用データ（`jpn_vert`）も配信するが、自動の向き判定は未実装                                                                                                                                                                                                   |
| 提出時の自動校正        | 提出確定で実行（run）を待ち状態で作る → 提出者などの端末が添付ごとに担当（期限付き）して文字を取り出す → **サーバーが版に記録したルールの版で照合し直す**（ブラウザの照合結果は使わない）→ 通常のコメントとして作成（投稿者はシステム `bot:proofreader`、表示名「自動校正」）。指紋で重複しない（再実行・再送でも増えない）。自動で解決済みにしない。返信・採否・持越は人の指摘と同じ。失敗しても提出は取り消さず、理由を残して再試行できる |
| 校了時の確認            | 未確認の自動校正があれば警告し、件数と任意のメモを校了の記録に残す（校了は止めない。既存の校了条件は変えない）                                                                                                                                                                                                                                                                                                                              |
| 任意の AI 校正          | 明示操作と送信先の確認ダイアログを経て、Convex action から外部 AI（Anthropic）に送る。キーはサーバーの環境変数だけ。キー未設定・無効・非公開の制作物では使えず理由を表示。結果は候補だけ（サーバーで本文に当てはめて確認、保存しない）。送信は監査ログに記録。提供元は `convex/lib/ai/provider.ts` で抽象化                                                                                                                                 |

## 3. 既存機能との統合

- 依存の向き: `apps/* → packages/application → packages/domain` を守る（業務ルールは domain、Convex はアダプタ）
- 自動校正の指摘は通常のスレッドなので、既存の返信・採否判断・担当・持越・通知・校了判定・監査がそのまま働く（持越しても「自動校正」の表示と根拠を引き継ぐ）
- 版の提出確定の 1 トランザクションで、ルールのスナップショットと自動校正の実行を作る。提出の冪等性はそのまま
- SNS の本文は文章の添付なので、既存の範囲指摘・文字の差分・自動校正が使える
- デモモードは同じ Convex 関数をブラウザ内で動かす（業務ロジックを二重に持たない）。デモにサンプルのルールと SNS の制作物を追加

## 4. AI を使わずに動く範囲

AI のキーが無くても、表記の検査（辞書・正規表現）、提出時の自動校正、OCR、版比較（文字・画像の類似度）、SNS のプレビューと書き出しはすべて動く。AI は「AI に校正の候補を出してもらう」ボタンだけ。版比較の AI 補助は未実装（§6）。

## 6. 未実装・未検証（実装済みと書かないもの）

- 版比較の AI 補助（ページ対応の候補を AI が出す）: **未実装**
- 形態素解析による検査: **未実装**（`detector: "morphology"` の型だけ用意）
- OCR の縦書き: 学習データは配信するが、ページの向き・縦書きの自動判定は**未実装**
- 自動校正のテキストは利用者の端末が取り出したもの。サーバーで PDF を開いて取り出し直すことはしていない（ルールの照合はサーバー）。悪意ある利用者が偽の文字を送ると、その利用者が書ける範囲の自動の指摘が作られうる（権限・件数上限・重複防止で抑止）
- AI 校正は実際の API での動作を**未検証**（キーが無い環境のため。キー未設定時の無効化と権限・機密区分の判定は試験済み）
- SNS の新しく選んだ画像は、提出するまで端末の中だけ（下書きを開き直すと選び直しが必要）。前の版の画像は引き継ぐ
- SNS のプレビューは各サービスの見た目の近似。実際の表示は実機で確認する
- 通知は最小限（提案・提案の結果・自動校正の完了）。メール・Slack は未対応
- 表（管理画面の一部）・投稿欄の入力欄・SNS プレビューの模擬画面は M3E に相当する部品が無いため独自の見た目のまま（[`UI_M3E.md`](UI_M3E.md) §21）

## 7. 本番で必要な設定

- Convex の環境変数（`apps/convex/.env.example`）: AI 校正を使う場合のみ `ANTHROPIC_API_KEY`（と必要なら `AI_MODEL`・`AI_ALLOW_RESTRICTED`・`AI_MAX_CHARS`）。**非公開の制作物を AI に送るかは制度上の判断**のため既定は送らない
- Nogiku Access で組織権限 `notation:manage` / `notation:category:<code>` を宣言する場合は、その付与を Nogiku 側で行う（未接続なら校正システムの管理画面でカテゴリ管理者を個人単位で設定）
- 表記ルールの正本の取り込み（MF100 のルール。MF99 のスプレッドシートは年度 99 として取り込み、MF100 に当てるものは確認して年度を付け直す）
- OCR の資産はビルド時に `apps/web/public/ocr` へ写される（`vite.config.ts` の `ocrAssets`）。配信先の容量（約 16MB）に注意
- 本番デプロイ・過去データ移行・外部への実データ送信は明示の承認まで行わない（`CLAUDE.md`）
