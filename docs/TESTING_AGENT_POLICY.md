# Coding Agent と E2E のテスト運用方針（2026-10-22）

> `docs/TEST_PLAN.md`（受け入れ条件 A-01〜A-20 との対応・「文言を確かめない」）を補う運用方針。PR #34 の案を、実装した内容に合わせて更新した。
> 時間の内訳と CI の構成は `docs/CI_CD.md`。エージェントの作業手順は pstack（`.claude/settings.json` で有効）とプロジェクトのスキル（`.claude/skills/`）。

## 目的と優先順位

1. 要件を満たすかを検証し、バグを検出できること。
2. 仕様と無関係な表示変更でテストを書き換えないこと（文言・見た目は確かめない。`docs/TEST_PLAN.md`）。
3. 変更に必要な範囲のテストを短時間で実行できること（手元・PR は数分以内）。
4. テストを書いたエージェントと実装を直したエージェントが、同じ誤解を共有したままマージしないこと。

**テストを通すために実装の不具合を放置する、または検証内容を弱めることは禁止。**

## テスト層の責務

| 層                               | 主に確認すること                                                    | 置き場所                                                 | いつ流すか                                        |
| -------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------- |
| domain（単体）                   | 締切の境界、版の遷移、校了の制約、ACL などの不変条件                | `packages/domain/src/__tests__`                          | 手元で常に（`pnpm test`）・PR                     |
| application（単体／統合）        | ユースケース、権限、冪等性、失敗とロールバック                      | `packages/application/src/__tests__`                     | 手元で常に・PR                                    |
| Convex / Hono（統合）            | 実際の関数・HTTP の契約、入力検証、認可                             | `apps/convex/convex/*.test.ts`、`apps/api/src/__tests__` | 手元で常に・PR                                    |
| 機能の E2E（決定的）             | 画面の操作で業務の流れが通ること（提出・割り当て・コメント・校了…） | `apps/web/e2e/specs/*.spec.ts`（Playwright Test）        | `@smoke` は PR、全部は main。触った機能は手元で   |
| 画面の撮影・a11y（回帰の目視用） | 全画面の撮影、axe（WCAG 2.1 A/AA）、細かな表示の検証                | `apps/web/e2e/screenshots.mjs`                           | main と手動。画面を大きく変えたときは手元で該当部 |
| 実環境の E2E（将来）             | 実 Convex・Workers・R2・Nogiku の連携                               | 専用のテスト環境を用意してから                           | 統合の境界を変えたとき                            |
| agentic QA（探索的・将来）       | 想定していない操作の経路、レイアウトの不自然さ                      | 試すなら tester-army/e2e をデモ版で（下記）              | 手元・手動のみ。CI の合否には使わない             |

`apps/web` の `--mode demo` は apps/convex の実際の関数を convex-test でブラウザ内で動かす。**これはブラウザ操作の統合テストであり、実インフラ全体の E2E が通ったことは意味しない。**

## 変更の種類と流すテスト

| 変更                                           | 流すもの                                                                                                                    |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 説明文・見た目だけ                             | `pnpm check`・`pnpm typecheck`。画面を `pnpm --filter @mf100/web screenshots`（`E2E_PART` で該当部）で目視。spec は直さない |
| domain / application の業務規則                | 先に変更前で落ちる単体テストを書く（pstack の `tdd`）。画面の操作が変わるときだけ該当 spec を足す・直す                     |
| Convex / API / R2 / 認可                       | 関数・HTTP の統合テスト。画面の流れに関わるなら該当 spec                                                                    |
| ルーティング・フォーム・エディタ・レスポンシブ | 該当機能の spec（`pnpm --filter @mf100/web e2e <ファイル名>`）と `e2e:smoke`                                                |
| 画面の部品（locator の手がかり）が変わった     | `e2e/support/app.ts` の部品を直す。spec を 1 本ずつ書き換えて回らない                                                       |
| 共通部品・認証・デプロイ                       | `pnpm --filter @mf100/web e2e`（全部）と、影響する部の `screenshots.mjs`                                                    |

## E2E の書き方（spec）

- **1 本の spec は 1 つの業務の流れ**。前提（版がある・校正者が割り当てられている・コメントがある）は `e2e/support/scenarios.ts` の手順で自分で用意し、**ほかの spec の結果に頼らない**。spec ごとに新しいページ＝新しいデモのデータから始まる。
- **画面の構造の知識は `e2e/support/app.ts` に集める**。M3E の部品・クラス名・ダイアログの開き方が変わったら、まずそこを直す。spec は「誰が・何をして・どうなるか」だけを書く。
- **振る舞いを確かめる**（pstack `principle-test-behavior-not-implementation`）。わざと壊したら落ちるか・内部を作り替えても通るかの 2 つで判断する。文言ではなく、要素・状態のクラスや属性・件数・URL・ユーザーが入れた値で確かめる（`docs/TEST_PLAN.md`）。
- **固定の待ち（`waitForTimeout`）は使わない**。`expect(...)` の自動の待ち・`expect.poll`・`waitForURL` を使う。M3E のメニューやダイアログの開閉の途中で押すと外れるので、そこだけ `app.settle()`。
- 「出ない」を確かめる前に、前提（読み込みが終わった・権限が決まった）を肯定的に確かめる。
- タグ: PR で必ず流す主要な流れは `@smoke`、それ以外の業務の流れは `@core`。校了と採否も `@smoke`（画面の門を PR に寄せる）。`@smoke` は増やしすぎない（PR の待ち時間）。
- 足したら `--repeat-each=3 --workers=4` で流して、並列でも揺れないことを確かめる。
- 不具合の回帰テストは、可能なら直す前に落ちること・直した後に通ることを確かめる（pstack `tdd`）。

## 受け入れ条件から E2E を作る手順（エージェント向け）

`.claude/skills/e2e-from-spec/SKILL.md` に手順をまとめた（kickflow の「手動テストから E2E を作る」と同じ考え方）。概略:

1. `docs/REQUIREMENTS.md`・`docs/TEST_PLAN.md`・`docs/DECISIONS.md` で仕様の根拠を確かめる。未承認の事項をテストで確定しない。
2. 確かめることが domain / application で済むならそちらに書く。E2E にするのは画面の操作でしか確かめられないものだけ。
3. `.claude/skills/verify-mf100-web/features/` と `e2e/specs/` で既にある検証を探し、重ならないようにする。
4. 前提を `scenarios.ts` で用意し、spec を書き、単独と並列で流す。
5. PR に「受け入れ条件 / 確かめる点 / spec / 流したコマンド / 結果 / 確かめていないこと」を書く。流していないものを通ったと書かない。

## 実行と CI

- 手元: `pnpm check`・`pnpm test`・`pnpm typecheck`、画面に触れたら `pnpm --filter @mf100/web e2e:smoke`（デモ版のビルドから自動）と該当 spec。
- PR: `verify` と `e2e-smoke`（`@smoke` と PWA）を同時に。
- main: `verify`、spec を shard に分けた `e2e` と報告をまとめる `e2e-report`、撮影と a11y の `visual`（部ごと）。
- 失敗の調査: Actions の成果物の HTML 報告に trace（操作ごとの DOM・ネットワーク・console）が入る。`pnpm exec playwright show-trace <trace.zip>`。
- flaky は隠さない: CI のやり直しは 1 回だけで、やり直して通ったものは報告に flaky として残る。直すまで放置しない。

## agentic testing（tester-army/e2e）の扱い

- 試すなら手元でデモ版に対して。1.0 前で API が変わり得るので版を固定する。
- 想定していない動線や表示の崩れを見つける用途に限る。ACL・校了の可否・データを壊す操作など**重要な仕様の合否は決定的な spec に残す**。
- CI の合否には入れない（実行のたびに結果と費用が変わるため）。入れるなら informational（失敗しても止めない）から。

## データと安全

- 使うのはデモのデータとデモのアカウントだけ。実データ・トークン・本番の認証情報を AI モデルや外部サービスに渡さない。本番環境に書き込むテストはしない（CLAUDE.md）。
- エージェントがテストに合わせて仕様を変えない。規則を変えるときは要件・決定ログを先に直す。
