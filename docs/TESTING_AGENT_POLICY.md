# Coding Agent と E2E のテスト運用方針（2026-10-22）

> 現行の `docs/TEST_PLAN.md` と受入条件 A-01〜A-20 を補完する運用方針。既存CIや実装を直ちに置き換えるものではない。

## 目的と優先順位

1. 要件を満たすかを検証し、バグを検出できること。
2. 仕様と無関係な表示変更でテストを書き換えないこと。
3. 変更に必要な範囲のテストを短時間で実行できること。
4. テストを書いた Coding Agent と実装を修正した Coding Agent が、同じ誤解を共有したままマージしないこと。

**テストを通すために実装の不具合を放置する、または検証内容を弱めることは禁止。**

## テスト層の責務

| 層 | 主に確認すること | 推奨配置 | ローカル実行 |
| --- | --- | --- | --- |
| domain（単体） | 締切の境界、版の遷移、校了制約、ACL 等の不変条件 | `packages/domain/src/__tests__` | 変更対象のテストから |
| application（単体/統合） | ユースケース、権限、冪等性、失敗とロールバック | `packages/application/src/__tests__` | 変更対象のテストから |
| Convex / Hono（統合） | 実際の関数・HTTP契約、入力検証、認可 | `apps/convex/convex/*.test.ts`、`apps/api/src/__tests__` | 変更対象のテストから |
| browser（決定的E2E） | 画面操作、ルーティング、表示状態、ファイル添付、レスポンシブ | `apps/web/e2e/` | 重要シナリオを選択 |
| real staging E2E（将来） | 実 Convex・Workers・R2・Nogiku の連携 | 専用テスト環境を用意してから | 統合境界に変更があるとき |
| agentic QA（探索的） | 未知の操作経路、レイアウトの不自然さ、未想定のUX不具合 | `e2e` 等を実験導入 | 原則ローカル/手動、CIは当面 informational |

`apps/web` の `--mode demo` は Convex の一部をブラウザ内で模擬実行する。**これはブラウザ操作の統合テストであり、実インフラ全体のE2E成功を意味しない。**

## 変更の種類と実行範囲

- 説明文・見た目のみ: `pnpm check`、web型検査、影響画面のブラウザ確認。業務条件に無関係な文言はassertしない。
- domain / application の業務規則: 最初に変更前で失敗する単体テストを用意し、境界値・拒否条件を確認する。UI操作が変わる場合だけブラウザ検証を追加する。
- Convex / API / R2 / 認可: 関数・HTTPの統合テストと、必要なら画面操作を追加する。実インフラの挙動が重要なら専用staging環境で確認する。
- ルーティング・フォーム・エディタ・レスポンシブ: 対象機能のブラウザシナリオを更新し、主要な導線のsmokeを回す。
- 共通コンポーネント・認証・デプロイ: 変更影響を確認し、広い回帰テストや手動確認を要求する。

## 受け入れケースから E2E を作る手順

1. `docs/REQUIREMENTS.md`、`docs/TEST_PLAN.md`、`docs/DECISIONS.md` を読んで仕様の根拠を確認する。未承認事項をテストで仕様確定しない。
2. 変更した機能、ユーザー操作、期待される観測結果、境界条件、既存テスト、対象環境、実行時間の目安を短い表にする。
3. E2Eで確認する必要があるものだけを選ぶ。重複した業務規則はdomain/applicationテストで確認する。新規の長いE2Eやテスト環境の追加には事前に方針を提示する。
4. 新しい不具合の回帰テストでは、可能な場合は修正前で失敗、修正後で成功を確かめる。既存仕様を変更する場合は仕様差分の根拠を明記する。
5. 独立したfixtureと専用データを作る。デモの状態が共有されるならテスト単位で初期化する。共有状態での並列実行を禁止し、分離できてから並列化する。
6. Playwrightのrole/label/test-idとweb-first assertionを優先する。曖昧な`.first()`・`.nth()`、CSS階層・固定sleepは、その必要性と代替手段を検討する。
7. 「表示されない」を検証する前に、対象画面の読込完了・権限の確定など、前提状態を肯定的に検証する。
8. 該当テストを複数回動かし、flakyがないか確認する。失敗時にはtrace・console・必要なスクリーンショットを保存する。
9. PRには「要求/観測点/テストファイル/実行コマンド/修正前後の結果/未検証事項」を記載する。未実行を成功と記載しない。

## MF100で優先する代表的シナリオ

- A-04 / A-17：締切時刻の直前・ちょうど・直後、次版確定後の旧版コメント拒否。境界はdomain/applicationで網羅し、ブラウザでは代表例を確認。
- A-08：重大未解決・専門確認未完了による校了不可と、許可された例外操作の監査。
- A-11：ACL剥奪直後に画面・API・添付を参照できないこと。
- A-02 / A-16：複数ファイルの一部失敗と再送、確定前のデータ不変性。
- UI：紙面の注釈の位置、狭幅でのはみ出し、キーボード操作、メニューからの復帰、入力欄のフォーカス。

## 実行・CI の方針

- 現行CIの `verify`、PRの `e2e-smoke`、mainの `core/compact/v2/web` を維持する。
- 既存 `apps/web/e2e/screenshots.mjs` はおよそ3,200行で、独立テストケースへの段階的移行候補。いきなり削除しない。
- `@playwright/test` で `*.spec.ts`、test fixture、trace、reporter、タグを整備したら、機能ごとに検証を移し、旧スクリプトと結果を照合してから置き換える。
- 並列化はfixtureの分離を先に実施する。タイミングの数値目標は実測（PR/main別の各jobの所要時間・flaky率）から決める。
- agentic testing の `e2e`（tester-army/e2e）は実験枠としてデモ環境から試す。1.0前でAPI変更の可能性があるため固定バージョンを使用する。未知の動線の発見には使うが、ACLや金銭・データ破壊を伴う重要仕様の合否判定は決定的アサーションを残す。
- Agentがテストに合わせて本番仕様を勝手に変えない。規約変更を伴うときは要件/決定ログを先に更新する。
- 専用のテストデータ・テストアカウントのみ使用。第三者の実データ、トークン、本番認証情報をAIモデルや外部サービスに渡さない。本番環境への書込みテストは行わない。

## 運用上の記録

新規シナリオごとに「受入条件ID・人間の言葉で書いた期待動作・責務を担うテスト・実行種別（PR/main/手動）・fixture・失敗時の調査方法」をテストファイルか対応ドキュメントに記録する。

この方針は2026-10-22時点のレビュー案。テストツールの変更や本番連携は、別PRで実行結果を確認して導入する。
