01 / DECISION

技術相談の要旨

委員会の既存実績を使い、新しい校正業務だけを実装する。技術スタックは React 19 + Vite + TanStack Router + Material 3 Expressive + Convex + Hono + R2 + Nogiku。

MF99 / 既存データ572件有効制作物・テスト除外後
MF100 / 負荷仮定17.2万件572制作物 × 6版 × 5人 × 10指摘
業務期間7か月11月〜5月。6〜10月はほぼ利用なし
重要な既存実績：MF99「UniQ」

ユーザー確認済み：NogikuとConvexの連携はUniQで実証済み。さらにUniQにはConvexセルフホストの手順と運用実績がある。接続できるかをゼロから調べるのではなく、既存実装をどう移植・共通化するかが検討対象。

最初はWeb / PWAとして提供する。デスクトップ専用ビルド（Tauri）は、OS連携が本当に必要と分かってから追加。開発と運用ではConvex Starter + R2を費用面の基準案とし、既存Convexセルフホスト環境の再利用も同格の比較対象に置く。

認証の実証済みという事実と、UniQのコードがそのままコピー可能という判断は別。Issuer設定、使用クレーム、ユーザー同期、権限失効時の動作、セルフホスト／Cloudでの差はコードを確認して決める。

業務知識と確定条件

概念 実際の意味
制作物（WorkItem） 広報文・ポスター・パンフ・UI・動画などの最終成果物。分類・担当・納期を持つ
版（Revision） 制作者が提出した内容の固定スナップショット。校正期限を持つ

担当の確認完了 代表者による確認の記録。期限による受付終了とは独立する
校了（FinalApproval） 権限を持つ一人が制作物全体の完成を宣言。未解決指摘があれば原則禁止、例外理由必須
制作・提出版を固定し受付開始
校正期間コメント・回答・担当確認
期限で閉じる未解決は残す
次版／校了改善または最終承認

動画・Webは最初から内部注釈を実装しない。版、担当、リンク、期限、最終承認だけ取り込み、必要時に外部校正画面を開く。

04 / SCOPE

内製範囲と既存資産の再利用

MF100で実装する

  • 制作物・版・受付期限・校了の状態管理、権限制御、監査記録
  • PDF.js等によるPDF・画像の注釈、コメントの担当・状態・優先度フィルター
  • Tiptap等の内部文章エディタ、版固定、既存の表記統一辞書によるチェック
  • 未解決指摘の次版引継ぎ（LLMは提案、人が確認）
  • HonoによるR2提出開始・完了確認・外部Webhook等の薄いAPI

新規に作らない／再利用する

  • Nogiku AuthのSSO。MF100独自のパスワード認証は作らない
  • Nogiku Accessの組織・グループ権限を可能な範囲で再利用
  • UniQのConvex連携実装・自己運用ノウハウを参照
  • 動画フレーム注釈・Webブラウザ内校正エンジンは初期段階で作らない
  • 独立したD1/Drizzleによる第二の業務DB、全面的な独自認証基盤は作らない
  • AIによる校了の自動実行、全コメントへの常時LLM呼出はしない

データの正本はConvex。Honoで同じCRUDを重複実装しない。校了権限はNogikuの組織権限と、制作物単位の担当指定・例外ルールを合わせて最終判定する。

05 / ARCHITECTURE

採用する技術構成と認証の境界

React 19 + Vite + TanStack RouterSPA / PWA。UIは @m3e/react を検証。PDF.js・Tiptap・TanStack Tableを画面別に導入
Convex Starter（業務の正本）WorkItem、Revision、Issue、権限判定、校了・監査イベント、リアルタイム購読
Hono on Cloudflare WorkersOIDCの必要な中継、R2署名URL、提出確定、Webhook。認証境界はUniQ実装を確認
Cloudflare R2 / NogikuR2は原本・プレビュー。Nogiku AuthはSSO、Nogiku Accessは組織権限
UniQの実績を設計インプットとして使う

MF99 UniQはConvexを使用し、委員会内にConvexセルフホスト手順、本番・sta運用の知見、ドメイン構成がある。NogikuとのSSO連携も実証済み（ユーザー確認）。このため、MF100は認証方式自体の探索ではなく、同じ認証連携パターンを流用できるかを確認する。

移植前にコードで確認する境界

既存実績 MF100への適用時に確認すること
Nogiku × ConvexのSSO連携は実証済み UniQのクライアント登録、issuer / audience、JWTクレーム、トークン更新、ログアウト、失効時動作。Cloud版・自己運用版の互換性
UniQのConvex自己運用手順が存在 監視、バックアップ、復元、アップグレード、共有基盤のリソース余力。UniQと同一インスタンスは前提としない
MF100固有のアクセス権限は要実装 利用者のNogiku IDと制作物担当者の関係、校了権限、年度切替、権限剥奪時の再認可

Cloudを選んだ場合もUniQの認証連携から学べるが、UniQは自己運用の実績があるため、同一設定でCloud Starterに移せるかを確認する。新たなIdPやパスワードDBを立てる設計にはしない。

09 / ADDITIONAL FIELD EVIDENCE

MFのNotionを横断して見つかった、設計に効く知見

過去3世代の校正システム、MF99の利用者アンケート、校了指針、表記統一ツール、システム局の引き継ぎを横断。ここに書く数値・失敗・運用例は資料に記載されたものであり、右側の「MF100への示唆」は設計提案である。

最重要の発見

MF100で解決すべき中心課題は「校正をオンライン化すること」ではない。正しい制作物に辿り着き、途切れず提出し、対面・オンラインの指摘を保全し、校了の責任を明示することである。Notion化で得た検索性は残し、75期システムで評価された軽さ・提出の容易さを取り戻す。

FIELD INSIGHT 01 / 75期フィードバック軽さと提出体験は旧システムの強みだった

75期の校正サイトは「軽い」「提出が楽」「過去版へ戻りやすい」と評価された。一方、重いAIファイルや多数ファイルの提出失敗、校了誤操作、コメント通知の不具合も報告された。

MF100への示唆：最初のPoCは美しいトップページより1版あたり複数ファイルの再開可能な提出・過去版表示・校了確認画面で検証する。

75期 校正システムのフィードバック
FIELD INSIGHT 02 / 99期振り返りNotionの検索性は残す価値がある

制作物を「担当」「制作担当」「関連担当」から検索でき、関係DBから参照できた点は高評価。一方、DBのフィルタ操作は重く、手動ID入力や有効性チェックによる状態の曖昧さが残った。

MF100への示唆：制作物と担当のリレーション、複数軸の検索、サジェスト、登録・承認の状態分離はMVPに含める。

FIELD INSIGHT 03 / 21人アンケート通知を全削除するのは誤り

21人回答の資料で校正リマインド回数は「多い」10人、「適切」11人。一方、必要性の設問では「必要」19人・「不要」0人。通知量への不満と、通知自体の必要性は両立している。

MF100への示唆：マイタスクを正本にし、未対応の人・期限が近い仕事・重要な状態変化にだけ通知する。担当ごとの頻度設定も検討。

FIELD INSIGHT 04 / 導入事故導入の遅れが二重運用を招いた

refineは2月下旬の運用開始になり、EVE合宿の制作物はSlackで版更新されてしまった。振り返りでは開発途中のユーザーフィードバック不足も反省として明示されている。

MF100への示唆：繁忙期（11〜5月）の直前に、新制度すべてを一斉切り替えしない。PR/EVE/SPIで小規模パイロットを行い、既存運用との移行境界を合意する。

refine 振り返りmtg
FIELD INSIGHT 05 / 正式な校了指針校了は単なる「コメントがゼロ」ではない

MF99の総論は校了を、目的達成と外部公開の適切さについて校了権限者が判断することと定義。媒体・制作担当・用途で権限者が異なり、制作者と校了権限者が同一となる一部ケースではPRs全員の合意という例外がある。

MF100への示唆：校了は最終的に1名の操作で確定できる設計としつつ、事前に要求する合議・例外承認・確認項目を制作物ルールとして表現する。「登録外の文書・企画対応物」も移行前に分類する。

校正・校了指針 総論
FIELD INSIGHT 06 / 文章校正「コメント未解決」は「未対応」と同義ではない

文章指針では、前版コメントを削除・解決済みにせず次版へ残す運用、反映しない指摘は理由をコメントする運用が示されている。指摘を次版にコピーするだけでは判断の状態が分からない。

MF100への示唆：未反映・対応済み・見送り理由あり・次版で再確認を履歴上区別する。LLMの引継ぎは「コピー」ではなく、元指摘IDを持つ候補生成と人の確認にする。

文章 校正・校了指針
FIELD INSIGHT 07 / notation表記統一エンジンは既に委員会に存在

notationは誤表記を規則で検出して置換候補を出す。改善要望には正規表現の重複マッチ、正表記を再検出する問題、ルールのUI登録、PR/Admの用途別ルール切替などがある。

MF100への示唆：表記チェックをLLMから作り直さず、notationの辞書と正規表現をデータとして移行する。版提出時のチェック結果とルール版を保存し、文脈の判断だけLLMへ。

notation 概要 · 改善要望
FIELD INSIGHT 08 / 0版制度ラフ・方向性確認は通常の校正と性質が違う

Web向けの「0版制度」では、Figmaや手書きラフを提出し、対面で方向性を検討することを推奨。初期段階で多案比較し、制作途中での大きな手戻りを避ける狙いがある。

MF100への示唆：「0版/ラフ」と「1版以降」を分ける。最初は画像/PDF/外部Figmaリンクと議論ログだけで十分。画面に完成度や自動校了の期待を持ち込まない。

0版制度設計
FIELD INSIGHT 09 / MF99 SYS引き継ぎセルフホストの安さと安全さは別物

システム局の引き継ぎではVPS保守負荷、監査ログ・バックアップの不足、アクセス権限の絞り込み、CI/CD、自動依存更新の重要性を挙げている。UniQにはConvexのセルフホスト運用実績がある。

MF100への示唆：Convex Starterとの比較は月額料金だけでなく、復元試験・担当2名以上・アクセス管理・監視・過年度データ削除規則を含める。既存基盤に空きがあることは採用条件の一つにすぎない。

システム局 引き継ぎ · UniQ Convexセルフホスト
FIELD INSIGHT 10 / 制度との緊張関係オンラインだけを正解としない

MF99の校正引き継ぎには、対面作業会を基本とし、その日の成果物を記録して次の作業までに追加校正する運用案がある。他方、遠隔で使いやすい個人別一覧も求められている。

MF100への示唆：同じ制作物に「対面で合意した指摘」「画面上での注釈」「Slack議論への参照」を追加できる。校正の現場を1つに強制せず、記録の正本だけを統合する。

完成宣言と承認規則 校了ボタンは責任ある単独操作。ただしルールに合議がある場合、必要な証跡がそろうまで警告・ブロック MF99には「制作者兼校了権者」の例外規則がある [source]
表記ルールの例外 誤表記でも広報文として意図的な場合は理由付きで無視できる 文章指針で意図的な逸脱のコメントが求められる [source]

開発工数と段階分け

開発時間の見積は工数上の仮定であり、採用技術や既存資産により大きく変動する。原本は共通開発・移行・試験420時間、初期機能180〜260時間、全体350〜600時間を例示していた。

段階 優先機能 工数への影響
PoC 認可、WorkItem、Revision、R2提出、PDF注釈 外部連携を増やさない。代表20件で検証
本運用 提出締切、校了、担当ダッシュボード、通知、監査、復元 運用品質の工数を削らない
文章 内部エディタ、版固定、表記統一辞書 共同編集を初期から求めるかで差が大きい
最適化 Jev分類、AI引継ぎ、媒体連携 誤判定評価・予算制御の工数を含む

見積はPoCで実際に使った時間を記録し再計算する。「開発者の趣味として面白い」と「年度内に保守できる」は別の基準で判断する。
